# REDESIGN2 widgets — legacy survey (consolidated)

This document is a consolidated, multi-run legacy survey of the REDESIGN2 widgets tree (`_______REDESIGN2/KDB3/js/dashboard/canvas/widgets/`). Each run appends one section covering a slice of the widget subsystem; sections are written independently and must not be edited by later runs. Target widget types in the new project: **text, visualization, topN, datatable**.

## RUN 1 — Lifecycle / Orchestration / Canvas / Routing (Layer A)

Scope read in full: `__widgetsOrchestrator.js`, `renderWidgetCycle.js`, `rescanWidgetState.js`, `resolveCanvasWidgetType.js`, `placeWidgetOnCanvas.js`, `placeAllWidgetControls.js`, `routeCanvasDropRequest.js`, `routeLaunchpadTransferRequest.js`, `configureLiveWidget.js`, `resolveLiveWidgetDataConfig.js`, `resolveVisualizationTarget.js`, `resolveControlWidgetDefaultBackground.js`, `resolveZoomFactor.js`, `recoverErrorWidget.js`, `setupWidgetRenderLoadingBridge.js`, `setupStelleHierarchyWidgetBridge.js`, `resetWidgetToLaunchpad.js`. Direct dependencies (toolbar/settings mount, per-type take/send, topN, history, hierarchy effects) are noted but deferred to other runs.

### Orchestrator wiring (`__widgetsOrchestrator`)
- **Entry signature**: `__widgetsOrchestrator__(_KDB)` — a single factory invoked with the global `_KDB` runtime object. No explicit destroy/unmount is exposed; teardown is per-widget (see `resetWidgetToLaunchpad`), not whole-subsystem.
- **On init it**:
  1. `ensureRegionState(_KDB)` — creates `_KDB.state.canvas.widgets.{subscriptions, didScheduleLaunchpadSync}`.
  2. `setupWidgetRenderLoadingBridge(_KDB)` — wires render→loading spinner bridge.
  3. `setupStelleHierarchyWidgetBridge(_KDB)` — wires dienststelle/hierarchy downstream into widgets.
  4. Subscribes a fixed set of event→route handlers (idempotent via `subscriptions[key]` guard).
  5. `applyWidgetSettingsButtonVisibility(_KDB)` immediately (initial paint).
  6. `scheduleInitialRoute(_KDB)` — one-shot: after `_KDB.state.launchpad.ready` resolves, routes ALL current canvas content back to launchpad (`routeAllToLaunchpad`). Guarded by `didScheduleLaunchpadSync` so it runs once.
- **Event subscriptions owned here** (all keyed in `_KDB.state.canvas.widgets.subscriptions`, each wrapped in `Promise.resolve(...).catch(log)`):
  - `LAUNCHPAD_SEND_REQUESTED` → `routeLaunchpadTransferRequest`
  - `LAUNCHPAD_TAKE_REQUESTED` → `routeLaunchpadTransferRequest`
  - `WIDGET_DROP_VALIDATED` → `routeCanvasDropRequest` (drop path entry)
  - `WIDGET_RESCAN_REQUESTED` → `rescanWidgetState(widgetId)` (no-op if `widgetId == null`)
  - `WIDGET_CLEANUP_REQUESTED` → `runWidgetVisualizationCleanup` (run 5/other)
  - `WIDGET_CONFIGURATION_CHANGED` → `syncWidgetSettingsUiFromState` (UI resync; skipped for `isHistoryReplay`, requires DOM el + `lifecycle === "active"`)
  - `WIDGET_SETTINGS_BUTTONS_VISIBILITY_REQUESTED` → `applyWidgetSettingsButtonVisibility`
- **Returns a small public API**: `routeAllToLaunchpad`, `routeRequest(eventName, request)`, `routeDropRequest(request, options)`, `requestSend(request)`, `requestTake(request)` (the last two just `emit` the corresponding launchpad events).
- **Request normalization**: `normalizeEventRequest` wraps bare values (string/number/DOM node/`getId()`-bearing object) into `{ widgetSource: value }`; object requests pass through. This lets every route accept either a widget id, a DOM element, a widget API object, or a structured drop payload.

### Widget lifecycle flow (create → placed → live → launchpad → reset)
Lifecycle string lives at `entry.lifecycle` and is the **last confirmed placement/use state**; in-flight interactions live under `entry.pending.*` (e.g. `pending.move`, `pending.configure`, `pending.render`), deliberately NOT reflected in the root lifecycle. Approved lifecycle values are enforced in `setWidgetSetting` (run 2). Values seen in this layer: `active`, `error`, `inLaunchpad`, `removed`.

1. **Type resolution** (`resolveCanvasWidgetType`): collapses many widget-type spellings into just two canvas buckets — **`"text"` or `"live"`** (everything non-text — LIVE/SHAPE/visualization/list/datatable — maps to `"live"`). Resolution order:
   - Inline hints first: `request.widgetType` / `request.type` (via `WIDGET.*` normalization), then `padKey` / `draggedElementType` / `launchpadSlot` (via launchpad-value mapping; splits on `_` and lowercases).
   - Then widget state's `launchpadSlot`, then `widgetSource.getType()`, `widgetApi.getType()`, `cognosAPI.getType(id)`, and finally async `cognosAPI.getWidgetWhenReady(id).getType()`.
   - Returns `null` if unresolvable (callers abort on null). **Note for new design**: legacy only has a binary text/live split here; the new four-type model (text/visualization/topN/datatable) is collapsed into "live" at this layer.
2. **Drop path** (`routeCanvasDropRequest`, triggered by `WIDGET_DROP_VALIDATED`): the big orchestration sequence —
   - resolve type → resolve dropbox el (`resolveDropboxEl`: by `dropboxId` via `_KDB.elements.dropboxById`, else match `tabId`, else first dropbox) → **take from launchpad** (`takeLiveWidgetFromLaunchpad`/`takeTextWidgetFromLaunchpad` with `suppressSuccessEvents: true`) → **place on canvas** (`placeWidgetOnCanvas`) → on placement fail, `restoreToLaunchpad` and abort.
   - `confirmWidgetStateAfterCanvasAppend`: records `entry.lastDropRequest`, `entry.lastDropPadKey`, sets lifecycle `active`, sets canvas placement (`dropboxId` + `pageContainerId` from `.tabpanel` ancestor), syncs layout, mirrors kennzahl payload metadata into settings + DOM attrs, clears `pending.drop`.
   - For non-text (live): `claimTopNHelperTable` (abort+restore if unavailable) → `syncWidgetVisualizationTypeToState` → `configureLiveWidget({reason:"drop"})` (abort+restore if not ok).
   - `emitSuccessEvents`: emits `WIDGET_TAKEN_FROM_LAUNCHPAD` and `WIDGET_DROPPED` with full payload (incl. `downstreamApplied` derived from configure diagnostic).
   - `placeAllWidgetControls` mounts toolbar/settings (best-effort, logs on fail).
   - History: `pushCommittedStep(buildWidgetDropHistoryStep(...))` unless `skipHistory`/`isHistoryReplay`.
   - Any thrown error → restore to launchpad + log.
3. **Launchpad transfer path** (`routeLaunchpadTransferRequest`, triggered by SEND/TAKE events): validates the event is send/take and has a subject, resolves type, then dispatches to per-type `send*ToLaunchpad` / `take*FromLaunchpad`. This is the simpler sibling of the drop route (no placement/configure).
4. **Take-back / reset** (`resetWidgetToLaunchpad`): see dedicated section below.

### Canvas placement & geometry (`placeWidgetOnCanvas` + helpers)
- **Layout source priority**: if `request.layout` already has string `left/top/width/height`, it's used verbatim (history-replay / restore path); otherwise computed from the drop (`resolveLayoutFromDrop`).
- **Coordinate math**: `leftPx = round((pointer.offsetX - dragOffset.x) * (1/scaleX))`, same for top. Falls back to `clientX - dropbox originLeft` when `offsetX/Y` missing (uses `dropboxGeometry.resolveDropboxMetrics`). Clamps to `[0, dropboxRect/scale - widgetDim]` so widget stays inside dropbox.
- **Scale**: `resolvePlacementScale` reads `placement.scaleX/scaleY`, falling back to `resolveZoomFactor()`.
- **`resolveZoomFactor`**: reads `sessionStorage["KDB_zoom"]`, else `.pageViewContent` inline `style.zoom`, else parses CSS `transform: matrix(...)` scale, else `1`.
- **Dimensions**: from `_KDB.properties.textWidgetPropObj` (text) or `visualizationsPropObj` (live) `defaultHeight/defaultWidth`; parsed to px via `_KDB.utilities.convertToPx`. Text default 75px high, live 200px high, 300px wide.
- **DOM ops**: sets el `style.left/top/width/height`, `dropboxEl.appendChild(widgetEl)`, verifies `parentNode === dropboxEl` (else fail), applies default background, then `cognosAPI.setLayoutPosition(widgetId, finalLayout)`. Returns `finalLayout` (truthy) or `false`.
- **Default background** (`applyDefaultBackgroundToNewWidget` + `resolveControlWidgetDefaultBackground`): only if no existing `backgroundColor`/`colour` setting. Resolution chain: runtime confirmed default (`_KDB.state.kdbControl.settings.defaults.{text|visualization}BackgroundColor` with `isConfirmed === true`) → property default (`*PropObj.defaultBackgroundColor`) → hardcoded global (`dropdownOptions.hardcoded.backgroundColor.default`, fallback `#ffffff`). Validated via `CSS.supports("color", ...)`. Writes el style, setting, and best-effort `cognosAPI.setContentPropertyValue(id, "fillColor", ...)`.
- **`placeAllWidgetControls`**: single drop-path entry that mounts (in ORIGINAL order) settings panel → toolbar → applies button visibility → binds settings panel → syncs settings UI from state. (Toolbar/settings internals are run 3.)

### Render + error discipline
- **`renderWidgetCycle`**: wraps `cognosAPI.renderWidget(id)` with lifecycle tracking under `entry.pending.render`. Generates a `cycleId` (`id:timestamp:rand`), marks `pending.render = {status:"loading", cycleId, ...}`, emits `WIDGET_RENDER_STARTED`. Awaits `whenRenderStart(id)` then `whenRenderComplete(id)`, each wrapped in `withTimeout(promise, timeoutMs, label)` (Promise.race vs setTimeout reject; `timeoutMs <= 0`/non-finite disables). On success: if still current cycle (`isCurrentCycle` checks `pending.render.cycleId`), mark `status:"idle"`, emit `WIDGET_RENDER_COMPLETED`. On error/timeout: mark `status:"error"` (if current cycle), emit `WIDGET_RENDER_FAILED`. Returns `{ok, widgetId, cycleId, error?}`. The **cycleId guard** prevents a stale render from clobbering a newer one's state. Returns `missingRenderApi` if `cognosAPI.renderWidget` absent.
- **`setupWidgetRenderLoadingBridge`**: subscribes RENDER_STARTED/COMPLETED/FAILED + `WIDGET_SENT_TO_LAUNCHPAD`. On start: mounts a `loadingService` spinner on the widget el, stores handle in `_KDB.state.canvas.widgets.renderLoadingByWidget[widgetId] = {cycleId, handle, startedAt}` (finishing any prior handle first). On finished/failed: only clears the spinner if the stored `cycleId` matches the event's cycleId (again cycle-guarded). On launchpad-sent: force-finishes any stored handle. All handlers wrapped try/catch (non-blocking bridge).
- **`recoverErrorWidget`**: dedicated recovery gateway (called from `rescanWidgetState` when `lifecycle === "error"`). `configureLiveWidget` is strict on `lifecycle === "active"`, so recovery does the single transition `error → active`, calls `configureLiveWidget({reason:"errorRecovery", skipHistory:true})` ONCE (single-shot, no recursion). On success clears `lastConfigureFailure`; on thrown error reverts to `error` and sets `lastConfigureFailure = "recoveryAttemptThrew"`. Returns `{ok, recovered, error}`.
- **`rescanWidgetState`**: idempotent drift detector (no history writes). Per widget id:
  - skip if `inLaunchpad`/`removed`; if `error` → delegate to `recoverErrorWidget`.
  - live + default dimension but non-default topN → reset topN to default.
  - live + `cognosAPI.getVisType(id)` differs from `settings.visualizationType` → `syncWidgetVisualizationTypeToState`.
  - handles stale `pending.configure`/`pending.topNCommit` (>`PENDING_STALE_MS = 120000` ms): rolls back topNCommit to `previous`, clears pending; probes hidden-datatable availability for `hiddenDataTableUnavailable`/`topNHelperClaimUnavailable` failures; allows recoverable re-configure after `missingParameterMapping`.
  - decides `needConfigure` (missing topN result values, missing slots diagnostic, or stale configure) and, if the DOM el exists, calls `configureLiveWidget({reason:"rescan", skipHistory:true})`.
  - finally `syncWidgetSettingsUiFromState` if active.

### `configureLiveWidget` (live binding engine — heavily depended on by this layer)
- Strict gate: requires `entry.lifecycle === "active"` and `entry.widgetType === "live"` (else `widgetNotActive`/`widgetNotLive`).
- **Compute-first / apply-second** design with a **sequence/supersession** guard (`markBindingPending` → `mySeq`; every phase re-checks `isBindingSequenceCurrent`, bailing with `superseded:true` if a newer configure started).
- Compute phase: `resolveLiveWidgetDataConfig` (+ overrides) → `resolveDataSourceId` (`cognosAPI.getDataSourceIdByPackageName`) → hierarchy snapshot (`reconcileConfirmedHierarchy.getConfirmedHierarchySnapshot`) → optional Top N helper (`applyLiveWidgetTopN` or the newer `__topNOrchestrator` when `reason==="topN"` && `useTopNOrchestrator`) → `buildBindingPlan`.
- Apply phase: `applyBindingPlan(_KDB, id, plan, mySeq)` does all visible-widget writes.
- Pending/diagnostic bookkeeping: `markPending("configure")`, `setConfigureFailure` (writes `pending.configure.error`, `configureDiagnosticSummary`, `lastConfigureFailure`), `setConfigureSuccess` (diagnostic summary incl. topN applied count + replayed flag; clears lastConfigureFailure).
- On success emits `WIDGET_CONFIGURATION_CHANGED` (`downstreamApplied:true`) and `WIDGET_CLEANUP_REQUESTED` (suppressed for history replay).
- Returns `createResult(ok, seq, superseded, error, extra?)`.

### `resolveLiveWidgetDataConfig` (data identity resolver)
- **State-first, DOM-bootstrap-fallback** model: reads `_KDB.state.widgets[id].settings` as canonical; `readDomKennzahlMeta(id)` (widget element attributes like `kdb_code`, `kdb_kennzahlentable`, `kdb_kennzahldisplay` in multiple casings) only fills gaps.
- Resolves: `kennzahlenTable` (required → `missingKennzahlenTable`), validates against `properties.visualizationsDataPropObj[table]` (→ `noVisualizationDataForTable`), `kennzahlCode` (required → `missingKennzahlCode`), `datasourceName` (settings → vData → table name), visualization (`resolveCanonicalVisualization` → `resolveVisualizationTarget`), maps to a prop bucket (`piePropObj`/`listPropObj`/`prognosePropObj`/`stackedBarPropObj`/`stackedColumnPropObj`/`linePropObj`) and slices it by table (→ `missingVisualizationTypeConfig`), plus `kennzahlSpecificSlotDefaultObj[code]` defaults, and `dimension`/`sequences`/`topN` (override → settings → `"default"`).
- Output is a flat config object with `ok` + `diagnostic`. Exposes `readDomKennzahlMeta` and `listVisualizationKeys` statics.

### `resolveVisualizationTarget` (vis-type canonicalizer)
- Pure resolver: given any vis token (label, cognosId, uiValue, etc.), normalizes (`normalizeToken`: lowercase, strip separators) and maps to a canonical label among **Prognose, StackedBar, StackedColumn, Line, Pie, List**. Reads catalog from `properties.visualizationsPropObj.visualizations` and hardcoded dropdown from `dropdownOptions.hardcoded.visualizations`.
- Hardcodes prognose cognos ids (`com.ibm.vis.custom.prognoseyearlinechart`, legacy `...prognoseyear`). Explicitly marks plain bar/column **unsupported** (`plainBarColumnUnsupported`). Returns `{ok, label, cognosId, uiValue, diagnostic}`.

### Launchpad take-back (`resetWidgetToLaunchpad`)
Tears down a placed widget and returns it to launchpad:
- `ensureEntry`; clear drill-through selection buffer (`drillThroughSelectionBuffer.clearForWidget`); snapshot for history (`snapshotWidgetForHistory`); `markPending("reset")`.
- **Dispose runtime handles**: `disposeListenerHandles(entry)` (calls each `entry.listeners[*]()` then resets `{}`), `disposeSubscriptions(entry, _KDB)` (`_KDB.events.unsubscribe(handle)` per `entry.subscriptions[*]`).
- **DOM teardown (jQuery)**: removes `[data-kdb-widget-toolbar]` and `[data-kdb-widget-settings-root|panel]`; destroys jQuery UI `draggable`/`resizable` if bound (`kdb-move-bound`/`kdb-resize-bound`).
- **Per-type transfer**: `cleanLiveWidgetForTransfer`+`sendLiveWidgetToLaunchpad` (or text equivalents). On error marks `pending.reset.error` and returns false.
- Clears `pending.reset`; snapshots after; pushes `widget_launchpadTransfer` history step (unless `skipHistory`). Returns true.

### Hierarchy bridge (`setupStelleHierarchyWidgetBridge`)
How dienststelle/hierarchy changes reach widgets:
- Subscribes 3 events (keyed in `_KDB.state.canvas.widgets.subscriptions`):
  - `STELLE_HIERARCHY_CONFIRMED_CHANGED` (filter event) → `onConfirmedChanged` → `applyWidgetDownstreamEffects(_KDB, snapshot)` (ALL widgets).
  - `WIDGET_TAKEN_FROM_LAUNCHPAD` → `onWidgetTaken` → `applySingleWidgetDownstreamEffect` (single widget), but skips if `downstreamApplied` or `dropboxId` already set.
  - `WIDGET_CONFIGURATION_CHANGED` → `onWidgetConfigurationChanged` → `applySingleWidgetDownstreamEffect`, gated to live+active widgets, non-replay, not already-applied, and only for actions `visualizationType|dimension|sequences|topN`.
- Snapshot source: `reconcileConfirmedHierarchy.getConfirmedHierarchySnapshot(_KDB)`. All handlers Promise-wrapped with error logging.

### Top surprises / complexity hotspots
- **Only two canvas types exist in legacy** (`text` vs `live`); visualization/topN/datatable are all "live" here. The new 4-type model will need a finer type axis than `resolveCanvasWidgetType` provides — type discrimination currently happens later via vis-type resolution and prop buckets, not at routing.
- **Drop is a long fragile sequence with multiple restore-to-launchpad rollback points** (take → place → claim topN helper → sync vis type → configure), each failure unwinding by sending the widget back. This is effectively a hand-rolled saga/transaction.
- **Sequence/supersession guard in `configureLiveWidget`** (`mySeq` + repeated `isBindingSequenceCurrent` checks) is subtle concurrency control; many early-returns with `superseded:true`. Easy to get wrong on reimplementation.
- **cycleId guards appear twice** (render state in `renderWidgetCycle`, loading spinner in the bridge) — stale-cycle protection is a recurring pattern worth a shared abstraction.
- **DOM attributes are a parallel source of truth** for kennzahl metadata (multiple casings `kdb_*`/`KDB_*`/`KDB_KENNZAHL*`), used as bootstrap fallback and written on drop — a legacy-compat smell.
- **Lifecycle vs `pending.*` split is deliberate but easy to misread**: active widgets stay `active` during move/configure/render; only `pending.*` reflects in-flight work. Recovery (`error → active`) is the only place lifecycle is toggled for recovery.
- **`scheduleInitialRoute` force-sends ALL canvas content back to launchpad on startup** (after launchpad ready) — a non-obvious global side effect of orchestrator init.
- **Vis-type resolution is fuzzy/token-based** (`normalizeToken`, substring matching) and explicitly rejects plain bar/column; prognose has hardcoded cognos ids and legacy aliasing.

### The shared `setWidgetSetting` substrate (depended on by every commit here)
All commits in this layer go through the `setWidgetSetting` module API rather than writing `_KDB.state.widgets[id]` directly:
- **Callable default export** `__setWidgetSetting__(_KDB, id, key, value)` writes one setting (e.g. `"colour"`, `"layout"`, `"maximized"`).
- **Statics used pervasively**: `ensureEntry`, `mergeSettings`, `cloneSettings`, `setLifecycle(_KDB,id,lifecycle,patch?)`, `markPending(_KDB,id,key,value)`, `clearPending(_KDB,id,key)`, `snapshotWidgetForHistory(_KDB,id)`, `setCanvasPlacement`, `syncLayoutFromPlacement`.
- **`APPROVED_LIFECYCLE` enum (authoritative, answers Run-1 open question)**: `active`, `inLaunchpad`, `removed`, `pending`, `loading`, `error`, `idle`. Note Run 1 only saw 4; the full set is **7**. Move/resize use a transient `pending` lifecycle during the drag and restore `active` on commit.
- **`snapshotWidgetForHistory` shape** (the canonical history payload — see History model below): `{ widgetId, widgetType, lifecycle, tabId, padKey (=lastDropPadKey), dropboxId, pageContainerId, canvasContext, settings (full clone), settingsSummary (picked: visualizationType/dimension/sequences/topN/titleText/text/colour/backgroundColor/layout/x/y/width/height), cognos:{visualizationType (live getVisType), slots, localFilters} }`. It is the **serializable core**; runtime handles (listeners/subscriptions/jQuery data) are NOT included.

### Interaction commits — how each is started & committed

Two distinct shapes exist: **(a) jQuery-UI drag interactions** (move, resize) where `start*` only *arms* a mode and the commit fires from the jQuery `stop` callback; and **(b) direct imperative commits** (maximize, layout, colour) called straight from toolbar/settings actions.

**Move** (`startWidgetMove` → `commitWidgetMove`)
- `startWidgetMove` = `enableWidgetMoveMode({mode:"oneShot"})`. Modes: `default`/`oneShot`(einmalig)/`persistent`(aan). Lazily inits jQuery `draggable` once (`kdb-move-bound` data guard, handle `[data-kdb-widget-move-handle]`, starts `disabled:true`).
- DOM-mounted **move handle** (`ensureMoveHandle`) is an injected `.resizeEdge.top.move` div with a `move.svg` icon, inserted next to the settings root; removed on disable.
- On drag `start`: caches scale meta (`resolveContainmentAndScale`: parent rect vs layout size → `scaleX/scaleY`, containment box), sets lifecycle `pending`, `markPending("move",{startedAt})`, stores **start snapshot** in jQuery data `kdb-move-history-start`, shows grid overlay (`.KDB_absoluteLayoutGrid`). `drag`/`start` divide ui positions by scale to undo zoom.
- On `stop`: 50ms `setTimeout` → `commitWidgetMove`. `commitWidgetMove` runs optional snap (`generalFunctions.checkSnap`), **merges `{x,y}` from `el.style.left/top`**, `cognosAPI.setLayoutPosition(id, {left,top})`, lifecycle→`active`, clears `pending.move`, takes **end snapshot**, and pushes history **only if x/y changed** → key **`widget_layoutMove`**.
- `persistMoveModeInState` stores non-default mode in `pending.moveMode`. Deferred-disable: if disable requested mid-drag, sets `kdb-move-disable-after-stop` and disables after stop.

**Resize** (`startWidgetResize` → `commitWidgetResize`)
- `startWidgetResize` = `enableWidgetResizeMode`. Lazily inits jQuery `resizable` (`kdb-resize-bound` guard; handles `n,e,s,w,ne,se,sw,nw`; `containment:"parent"`). **Min size by type**: text `{100,50}`, else (live) `{300,300}`.
- `resize` callback compensates zoom (`resolveZoomFactor` reads `sessionStorage.KDB_zoom` → `.pageViewContent` style.zoom → 1) clamped to mins.
- On `start`: lifecycle `pending`, `markPending("resize",{startedAt})`, seeds settings from DOM (`readCurrentWidgetLayoutFromDom`), stores **start snapshot** (`kdb-resize-history-start`), grid overlay on.
- On `stop`: `commitWidgetResize` reads current size (`readCurrentResizeSize`, min-clamped), writes `el.style.width/height`, merges `{width,height}`, `cognosAPI.setLayoutPosition(id, layoutFromSettings)` (full left/top/width/height), lifecycle→`active`, clears `pending.resize`, **pushes history only if w/h changed** (dims normalized to px) → key **`widget_layoutResize`**.
- `markPending("resizeMode", meta)` tracks the *armed* mode separately from the in-flight `resize`. Disable mirrors move's deferred pattern.

**Maximize** (`startWidgetMaximize` / `endWidgetMaximize` — apply; `commitWidgetMaximize` — orchestrates + history)
- This is a **focus/expand-mode** toggle, NOT a layout resize. `startWidgetMaximize` (async) calls `cognosAPI.enterWidgetFocusMode(id)`, then awaits render (`waitForRenderIfAvailable`: race `whenRenderStart`/900ms then `whenRenderComplete`/1200ms) and polls `waitForExpandedState` (DOM `.expandModeContainer` presence). On success binds a **collapse-restore listener** (clicking the focus-mode collapse button disposes the focus settings panel) + `focusModeSettingsPanel.bind`. Idempotent if already expanded.
- `endWidgetMaximize` (async) calls `cognosAPI.exitWidgetFocusMode(id)`, waits for collapse, disposes the collapse listener + focus settings panel; warns (console) if still expanded after.
- `commitWidgetMaximize` (async) is the history-bearing entry: gated on `lifecycle==="active"`; takes `oldSnap`; resolves target via `options.targetMaximized` else toggles current; `markPending("maximize",{startedAt,target})`; calls start/end maximize; on success writes setting **`maximized`** (boolean); `clearPending("maximize")`; **pushes history only if `beforeExpanded !== targetExpanded`** → key **`widget_maximizeToggle`** (guarded by `skipHistory`/`isHistoryReplay`); emits `WIDGET_CONFIGURATION_CHANGED {action:"maximize"}`. **Rollback**: on apply failure or thrown error just clears the pending and returns false (no setting write).

**Layout change** (`commitWidgetLayoutChange` — imperative)
- Gated `lifecycle==="active"`; non-empty `layoutId`. `markPending("layout", true)`.
- **Text path**: `applyTextWidgetRestyle(_KDB,id,layoutId)` (abort+clearPending if not `true`). **Live path**: `cognosAPI.setContentPropertyValue(id, "com.ibm.vis.layout", layoutId)`.
- Writes setting **`layout`**, clears pending, pushes history → key **`widget_layoutChange`** (before any reconfigure, guarded). **Then for live**: awaits `configureLiveWidget({reason:"layout", skipHistory:true})` and returns its `ok`. For text: emits `WIDGET_CONFIGURATION_CHANGED {action:"layout"}` + `WIDGET_CLEANUP_REQUESTED`.

**Colour change** (`commitWidgetColourChange` — imperative, async)
- Gated `lifecycle==="active"` + DOM el present. Heavy **colour normalization**: `normalizeHexLiteral` (3/4/6/8-digit hex), `normalizeRgbFunction` (rgb/rgba→hex8), and **token resolution** `resolveCommittedColour`: `"default"`→default option hex, `"none"`→page background hex (`readPageBackgroundColourHex` from `.pagegenericPage` computed style, fallback `#ffffff`), else matches `backgroundColorDropdownShared.buildBackgroundColorOptionList` labels, else normalized literal.
- `oldSnap`; `markPending("colour", true)`; writes setting **`colour`**, sets `el.style.backgroundColor`, mirrors `cognosAPI.setContentPropertyValue(id,"fillColor",c)`. **Rollback on throw**: restores prior `colour` setting + DOM inline bg (from `beforeColour`/`beforeDomInline`), clears pending, returns false.
- Pushes history → key **`widget_colourChange`** only if `!coloursEqual(beforeColour, c)` (hex-normalized compare). Emits `WIDGET_CONFIGURATION_CHANGED {action:"colour"}` + `WIDGET_CLEANUP_REQUESTED`.

**State written by commits (summary)**: placement (`settings.x/y/width/height` + `cognosAPI.setLayoutPosition`), `settings.layout` (+ `com.ibm.vis.layout` cognos prop), `settings.colour` (+ `el.style.backgroundColor` + `fillColor` cognos prop), `settings.maximized` (+ cognos focus mode). Note settings use **`colour`** (not `bg`/`backgroundColor` for writes, though `backgroundColor` is read as fallback). `pending.*` keys used: `move`, `moveMode`, `resize`, `resizeMode`, `maximize`, `layout`, `colour`. **Every commit clears its own pending key on both success and failure.**

**Which commits push history**: move (`widget_layoutMove`), resize (`widget_layoutResize`), maximize (`widget_maximizeToggle`), layout (`widget_layoutChange`), colour (`widget_colourChange`) — each only when a real change occurred and not under `skipHistory`/`isHistoryReplay`. Drop (`widget_canvasDrop`) and launchpad transfer (`widget_launchpadTransfer`) are pushed elsewhere (Run 1 / reset path) but **replayed** by these adapters.

### History model — adapters, step shapes, replay

**Step builders (committed step shape)**
- `buildWidgetActionHistoryStep(key, oldSnap, newSnap)` → `{ key, timestamp, old: clone(oldSnap), new: clone(newSnap) }`. `old`/`new` are full `snapshotWidgetForHistory` payloads. Clone via `JSON.parse(JSON.stringify(...))` (drops non-serializable runtime fields automatically).
- `buildWidgetDropHistoryStep(_KDB, request, takeResult)` → `{ key:"widget_canvasDrop", timestamp, old, new }`. **`old`** is a synthetic *launchpad* snapshot (`buildOldLaunchpadSnapshot`: `lifecycle:"inLaunchpad"`, empty settings, null cognos, padKey/launchpadSlot/originId/payload/sourceKind). **`new`** is the live post-drop snapshot **augmented** with `layout/padKey/draggedElementType/originId/payload/sourceKind` (drop-replay needs these to re-route).

**Project historyService integration (the contract)**
- A step is pushed via `_KDB.history.pushCommittedStep(step)` (a.k.a. the project `historyService` API from `createHistoryApi`).
- Replay dispatch: `resolveHistoryHandler(step.key)` maps key → an adapter object exposing **`apply(...)`**. `createHistoryApi.applyStepValue(direction, step)` computes `targetValue = direction==="undo" ? step.old : step.new` and calls **`handler.apply(_KDB, targetValue, step, { direction })`**. It skips when `old`/`new` are equal. So undo/redo is symmetric: both restore a full snapshot, direction just selects which.
- **Two adapters, two `apply` signatures**:
  - `__widgetActionHistoryAdapter.apply(_KDB, targetValue, step)` — handles the 11 in-place action keys (`widget_launchpadTransfer`, `widget_layoutMove`, `widget_layoutResize`, `widget_colourChange`, `widget_layoutChange`, `widget_maximizeToggle`, `widget_textEdit`, `widget_liveTopNChange`, `widget_liveDimensionChange`, `widget_liveSequencesChange`, `widget_liveVisualizationTypeChange`). It is a thin guard that delegates to `applyWidgetActionHistorySnapshot(_KDB, step.key, targetValue)`.
  - `__widgetDropHistoryAdapter.apply(_KDB, stepValue)` — handles **`widget_canvasDrop`**. Uses only `targetValue.lifecycle`: `inLaunchpad`→`sendWidgetToLaunchpad`; `active`→`routeCanvasDropRequest({...isHistoryReplay:true, layout, dropboxId, padKey, payload, sourceKind:"historyReplay"}, {skipHistory:true})`. (Note `resolveHistoryHandler` registers `widget_canvasDrop`→drop adapter and the 11 action keys→action adapter via a `WIDGET_ACTION_KEYS` map.)

**`applyWidgetActionHistorySnapshot(_KDB, key, snap)` — the central replay engine (async)**
- Early `widget_launchpadTransfer` branch mirrors the drop adapter (send to launchpad vs re-route drop), so launchpad-transfer steps replay through the *action* adapter even though they're transfer-shaped.
- Otherwise restores from snapshot in order: `setLifecycle(snap.lifecycle, {tabId,widgetType})` → `setCanvasPlacement` (from `canvasContext` or `dropboxId`/`pageContainerId`) → `mergeSettings(sanitizeSettingsForReplay(key, snap.settings))`. **`sanitizeSettingsForReplay`** strips `width`/`height` for `widget_layoutMove` (move must not resize).
- **DOM application is key-aware**: resize→`applyDomResizeDimensions`, move→`applyDomMovePosition`, other layout→`applyDomLayout`; colour→`el.style.backgroundColor = resolveReplayColour` (else `applyColourToDom`). Then `cognosAPI.setLayoutPosition` (position-only for move, full for resize/layout), `fillColor` mirror, `setTitle`/note text for text, `com.ibm.vis.layout` for layout-change, focus-mode start/end for maximize, `setVisType` for live.
- **TopN/dimension coupling**: replaying `widget_liveTopNChange`/`widget_liveDimensionChange` with a default/none dimension resets `topN→"default"` and clears `topNResultValues`.
- Clears all pending keys (move/resize/configure/maximize/visualizationType/dimension/sequences/topN). Emits replay `WIDGET_CONFIGURATION_CHANGED`+`WIDGET_CLEANUP_REQUESTED` for colour/maximize/text/layoutChange (mapped action names).
- **Reconfigure decision**: for live+active widgets, if key is NOT one of move/resize/maximize/text/colour/launchpadTransfer → awaits `configureLiveWidget({reason:"historyReplay", isHistoryReplay:true, skipHistory:true, useStoredTopNValues: key===widget_liveTopNChange})` and fails if not ok. Else for live, `syncWidgetVisualizationTypeToState`. Finally `syncWidgetSettingsUiFromState` if active. This means layout/colour/text/move/resize replays are "cheap" (no re-bind) while data-shape changes (topN/dimension/sequences/visType) force a full reconfigure.

### Top surprises / complexity hotspots
- **History start-snapshots are stashed in jQuery `.data()`** (`kdb-*-history-start`) between drag-start and the deferred commit, not in `_KDB.state`. A teardown/re-render between start and stop would silently drop the snapshot (→ no history step). Fragile coupling of history to DOM element lifetime.
- **Move commit fires from a 50ms `setTimeout` inside jQuery `stop`** — and that same timer also handles deferred move-mode disable. Timing-dependent; reimplementation must preserve commit-before-disable ordering.
- **`maximized` is a boolean setting but maps to Cognos focus/expand mode**, not a layout geometry change — it interleaves async render-waits and DOM-polling (`waitForExpandedState`) into the history commit. The only history key here that awaits external async UI state.
- **Two adapters but launchpad-transfer is handled in both** (`widget_launchpadTransfer` early-branch inside the action snapshot mirrors the drop adapter). Drop uses `widget_canvasDrop`; transfer uses `widget_launchpadTransfer`; the split between "drop" and "transfer" history is non-obvious.
- **Symmetric snapshot-based undo/redo**: there is no inverse-operation logic — both directions just `apply` a full confirmed snapshot (old vs new). All the intelligence is in `applyWidgetActionHistorySnapshot` re-deriving DOM/cognos/configure from settings. Replay can therefore trigger a **full `configureLiveWidget`** for data-shape keys (expensive) but is cheap for move/resize/colour/text.
- **Colour token vocabulary is rich**: `default`, `none` (→ page bg), named labels, hex 3/4/6/8, rgb/rgba — all normalized to hex. `none` resolving to the *computed page background* is a surprising semantic.
- **Zoom/scale compensation is duplicated** across move (`resolveContainmentAndScale`) and resize (`resolveZoomFactor`) with different strategies (parent-rect ratio vs sessionStorage/style.zoom). Inconsistent zoom sources.
- **Min-size and default dims are hardcoded per text/live** (text 100×50, live 300×300) — consistent with Run 1's binary type split; the new 4-type model will need per-type min/default sizing.

### The "toolbar" is just a settings-gear button (not a real toolbar)
- **`buildWidgetToolbar`** produces ONE DOM node: `div.KDB_widgetSettingsButton[aria-label=WidgetSettings][data-kdb-widget-toolbar=<id>]` containing an `<input type=image class=svgIcon src=settings.svg data-kdb-widget-settings-toggle=1>`. It adds class `textWidget` for text, else `liveWidget`. **There are no per-action toolbar buttons here** — all real action controls live in the settings panel. So "which buttons per widget type" at the toolbar layer = just the single gear, type only affects a marker class.
- **`placeWidgetToolbar`** mounts it into the widget header: prefers `.widgetContentWrapper .widgetHeader` (or `.widgetHeader`), finds/creates a `.widgetIcons` div, and `insertAdjacentElement("afterbegin", tb)` so the gear is first icon; falls back to header/widget root append. Idempotent (bails if `[data-kdb-widget-toolbar]` already present). Forces `position:relative` if computed static. Then calls `bindWidgetToolbar`.
- **`bindWidgetToolbar`** adds a single `click` listener on the gear: locates the sibling panel (`[data-kdb-widget-settings-root="<id>"]` or `.KDB_widgetSettings`) and **toggles `.KDB_visible`** on it; on close it also strips `.KDB_visible` from any open `.KDB_IconsDropdown`. Stores `entry.listeners.toolbarDispose` for cleanup. So the gear is purely an open/close affordance — visibility is CSS-class driven, not state-driven.
- **`applyWidgetSettingsButtonVisibility`** is a GLOBAL, dashboard-wide gate, not per-widget. It toggles class `KDB_hide` on **all** `.widget .KDB_widgetSettingsButton` under the dashboard frame (`_KDB.elements.dashboardFrame()` else `document`). Hidden-ness comes from the payload's `isHidden` boolean, else from `_KDB.state.kdbControl.settings.dashboard.areSettingsButtonsHidden`. (Run 1 noted it's called at orchestrator init and on `WIDGET_SETTINGS_BUTTONS_VISIBILITY_REQUESTED`.) It only hides the *gear*, not individual settings actions.

### Settings panel — build / place / bind
- **`buildWidgetSettingsPanel`** builds `div.KDB_widgetSettings` (hidden until `.KDB_visible`) with `data-kdb-widget-settings-root=<id>` and `data-kdb-widget-type` = `text` or `live`. A `buildSettingsRoot` header row has an info button (`KDB_widgetInfoButton`), a fixed German title strip "Einstellungen", a `.widgetIcons` action container, and a `badgeContainer`. Each action is an **`iconShell`** = `div.dataWidgetIcon.liveWidgetAnnotations` with `role=button`, `tabindex=0`, `aria-label` (the action key), `data-kdb-settings-icon-action` (only for direct-action icons: `title`,`resize`,`maximize`,`reset`), optional `table-name`, a native `title` tooltip (German `TITLE_DE`), and an image icon (with multi-candidate fallback `png→svg→fallback`). Icons that open a dropdown get an `appendDropdownShell` (`div.KDB_IconsDropdown.<container>`).
  - **Live icons** (`appendLiveIcons`): backgroundColor, visualization, dimensions, sequences, topN, restyle(=layout), move, resize, maximize, reset (delete). dimensions/sequences carry the resolved `table-name`.
  - **Text icons** (`appendTextIcons`): text(=title), fontSize, backgroundColor, restyle(=layout), move, resize, reset. **No visualization/dimensions/sequences/topN/maximize** for text.
  - **Dropdown population** (per type): live → background color, visualization (from `dropdownOptions.hardcoded.visualizations`), dimensions+sequences (from `properties.visualizationsDataPropObj[table].{dimensions,sequences}`), topN (from `hardcoded.topN`), layout (`hardcoded.restyle`), move (hardcoded 3 modes default/einmalig/aktiv). text → title (single "default" reflecting current titleText/text), fontSize (`hardcoded.fontSize`), background color, layout, move. Options are `div.dataWidgetIcon[data-kdb-dropdown-kind][data-kdb-option-key][data-kdb-option-value]`, marked `.KDB_optionSelected`. **No native `<select>`** — entirely custom DOM dropdowns. Selection is computed against state at build time (visualization via `resolveVisualizationTarget`, colour via `backgroundColorDropdownShared.normalizeHexForCompare`, dim/seq/topN via default-token tests).
- **`placeWidgetSettingsPanel`** inserts the panel as the **first child of `.widgetContentWrapper`** (ORIGINAL `setWidgetAdditions`) else appends to widget root. Idempotent; forces `position:relative`; **never adds `.KDB_visible`** (CSS hides until toggled).
- **`bindWidgetSettingsPanel`** is the heavy controller (Run 1's `placeAllWidgetControls` calls place→bind). It wires the panel and is where **every settings action is dispatched to a Run-2/3/4 commit**. Key behaviors:
  - Guards: bails if no root or already `data-kdb-settings-bound=1`; sets it at the end.
  - **Dropdown option commit** (`runOptionCommit`, capture-phase `pointerdown` on options): reads `kind`/`key`/`value`, snapshots `before = cloneSettings`, sets `optionBusy` lock, and dispatches by `kind`:
    - text+`fontSize` → `commitTextWidgetFontSizeChange` (run 4/text). text+`title` → no-op (title handled by icon, see below).
    - `move` → `applyMoveModeSelection` (enables/disables `startWidgetMove` mode; keeps dropdown open).
    - `layout` → `commitWidgetLayoutChange` (skips if equal to current).
    - `backgroundColor` → `commitWidgetColourChange`.
    - live+`visualization` → resolve via `resolveVisualizationTarget({key,value})` then `commitVisualizationTypeChange`.
    - live+`dimension` → `commitDimensionChange`; live+`sequences` → `commitSequencesChange`.
    - live+`topN` → **dimension↔topN coupling guard**: if current dimension is default AND requested topN is non-default, it *reverts the UI* (re-syncs from `before`) and refuses; else `commitTopNChange`.
    - After: if `ok` → `syncWidgetSettingsUiFromState` from new state; else re-sync from `before` (rollback UI). On throw → re-sync from `before`.
  - **Direct-action icons**: `onPanelClick` handles `data-kdb-settings-icon-action`: `title`(text)→`scheduleTextEditStart` (50ms deferred `startTextWidgetTextEdit`), `reset`→`resetWidgetToLaunchpad`, `resize`→`startWidgetResize({reason:"settingsResizeButton"})`, `maximize`→`commitWidgetMaximize`. **This answers Run-2's open question: the settings panel (not a separate toolbar) is what calls `commitWidgetMaximize`/`commitWidgetLayoutChange`/`commitWidgetColourChange` and arms `startWidgetMove`/`startWidgetResize`.**
  - **Dropdown open/close + focus management** is intricate: capture `pointerdown` on the root toggles the icon's dropdown (closing others first); a document-level capture `pointerdown` closes dropdowns/move/resize when clicking outside; `focusout` arms a 180ms deferred close (deferred further by recent interaction timestamps `shouldDeferFocusOutClose`). Move mode auto-arms `oneShot` when the move dropdown opens in default mode; one-shot move auto-disables on focus loss. Disposal (`settingsPanelDispose`) removes all listeners and disables non-persistent move + resize modes.

### `focusModeSettingsPanel` — settings inside Cognos full-screen ("focus mode")
- "Focus mode" = Cognos **expand/maximize** mode (`.expandModeContainer`, entered via `commitWidgetMaximize`→`startWidgetMaximize`→`cognosAPI.enterWidgetFocusMode`; Run 2). When a live widget is maximized, the normal in-canvas settings panel is not in the expanded DOM, so this module **clones a reduced settings panel into the expanded container**.
- `bind(_KDB, id, widgetEl)`: resolves the canvas widget, its source `.KDB_widgetSettings` panel, the `.expandModeContainer`, and the expanded `.KDB_widgetSettingsButton`. It **deep-clones the source panel** (`buildFocusPanelFromSource`), strips all icons except an allow-list (**info, visualization, dimensions, topN** — i.e. NO move/resize/maximize/reset/sequences/colour/layout in focus mode), re-tags it `KDB_focusModeSettingsPanel` / `data-kdb-focus-mode-settings-root`, mounts it before the header, syncs selection from state, and binds its own pointer handlers.
- Its option commits (`commitOption`) only support **visualization, dimension, topN** → `commitVisualizationTypeChange`/`commitDimensionChange`/`commitTopNChange`; after each it re-syncs BOTH the focus panel (`syncFocusPanelUiFromState`) and the canvas panel (`syncWidgetSettingsUiFromState`). Dropdowns are **clamped to the expanded widget's bounding rect** (`clampFocusModeDropdown`) so they don't overflow the full-screen container. The gear button toggles the focus panel's `.KDB_visible`; outside-click closes it. `dispose` removes listeners and the cloned panel; the dispose fn is stored in `entry.listeners.focusModeSettingsDispose` (bound/unbound by maximize enter/exit in Run 2).

### `syncWidgetSettingsUiFromState` — state→UI projection (no writes)
- Pure projection: reads canonical settings (`cloneSettings`, or an explicit `settingsOverride` snapshot for rollback UI), finds the panel root, and sets `.KDB_optionSelected` markers on each dropdown to match state. **Live**: visualization (via `resolveVisualizationTarget`→uiValue), dimension/sequences (default-collapsed to `"default"`), topN (matched by `data-kdb-option-key`, default-collapsed), layout, background color (hex-normalized compare). **Text**: title (always "default"), fontSize, layout, background color. Also updates the title strip text. Exposes static helpers `isDefaultDimVal`/`isDefaultTopNVal`/`isDefaultSequenceVal` (treat `""`/`"default"`/`"none"` as default) — reused by `bindWidgetSettingsPanel` and `focusModeSettingsPanel`. Subscribed to `WIDGET_CONFIGURATION_CHANGED` by the orchestrator (Run 1) for non-replay resyncs.

### Setting writes — what each commit does
All commits gate on `entry.lifecycle === "active"` and (except text) `widgetType === "live"`, require the DOM el to exist, snapshot old/new via `snapshotWidgetForHistory`, and push history through `buildWidgetActionHistoryStep` unless `skipHistory`/`isHistoryReplay`.

| Commit | Writes to `settings` | Validation | Reconfigure | History key |
|---|---|---|---|---|
| `commitDimensionChange` | dimension (written **inside** `configureLiveWidget` via override, not directly) | `dimensionIsAllowed` against `visualizationsDataPropObj[table].dimensions` | `configureLiveWidget({reason:"dimension", dimension, [topN, topNResultValues]})` | `widget_liveDimensionChange` |
| `commitSequencesChange` | sequences (written **directly** via `setWidgetSetting`) | `sequenceIsAllowed` against `…[table].sequences` | `configureLiveWidget({reason:"sequences"})` | `widget_liveSequencesChange` |
| `commitVisualizationTypeChange` | visualizationType (written **inside** configure via `syncWidgetVisualizationTypeToState`/plan, not directly here) | `resolveVisualizationTarget(...).ok` | `configureLiveWidget({reason:"visualizationType", visualizationType: target.label})`; clears `pending.configure` | `widget_liveVisualizationTypeChange` (only if snapshots differ) |
| `commitWidgetTextEdit` | `titleText` (live, + `cognosAPI.setTitle`) **or** `text` (text widget, + DOM `.note-editable p`) | el present | live → `configureLiveWidget({reason:"text"})`; text → emits `WIDGET_CONFIGURATION_CHANGED{action:text}` + `WIDGET_CLEANUP_REQUESTED` | `widget_textEdit` (pushed **before** reconfigure) |

- **dimension↔topN coupling is explicit here**: `commitDimensionChange` resets `topN→"default"` and clears `topNResultValues` (via configure overrides) whenever the new dimension is a default/none value. The UI-side guard in `bindWidgetSettingsPanel` additionally refuses to set a non-default topN while dimension is default. (Run 2 also noted history replay re-applies this coupling.)
- **`syncWidgetVisualizationTypeToState`** (used by configure/rescan, not a user commit): reads `cognosAPI.getVisType(id)` (retries once after a microtask if empty), maps via `resolveVisualizationTarget` to a canonical `label`, and writes `settings.visualizationType` (or clears it if empty). This is why `commitVisualizationTypeChange` doesn't write the setting itself — Cognos is the source of truth for the applied vis type, and the configure round-trip pulls it back into state.
- **Asymmetry worth noting**: sequences/text write the setting *directly*; dimension/visualizationType delegate the write to `configureLiveWidget` (state is reconciled from the apply result). So `settings.dimension`/`settings.visualizationType` are *configure-authoritative*, while `settings.sequences`/`settings.titleText`/`settings.text` are *commit-authoritative*.

### Settings mapped to the 4 target types (text / visualization / topN / datatable)
Legacy only distinguishes **text vs live** (Run 1), so all of visualization/topN/datatable collapse into "live" here:

- **visualization (live)**: visualizationType, dimension, sequences, topN, backgroundColor, layout, move, resize, maximize, reset.

### Assessment — is there a cohesive "widget settings" capability?
**Mostly yes — there is a recognizable shared "widget settings" submodule, but it is not cleanly factored.** Evidence for cohesion:
- A single panel builder + binder + state-sync trio (`build/place/bind` + `syncWidgetSettingsUiFromState`) drives ALL settings UI for both text and live, with a shared option-row/dropdown DOM contract (`data-kdb-dropdown-kind/-key/-value`, `.KDB_optionSelected`) and shared default-token helpers.
- `focusModeSettingsPanel` *reuses* the same panel by cloning + filtering — strong signal the panel is a reusable unit.
- All writes funnel through `setWidgetSetting`, and all commits share the same shape (gate→snapshot→configure→history).

Against a clean "service":
- The binder (`bindWidgetSettingsPanel`) is a 590-line controller hard-wired to ~10 specific commit modules across runs 2/3/4 (move, resize, maximize, layout, colour, vis, dim, seq, topN, text, reset). It is a dispatcher, not a generic registry.
- text vs live branching is duplicated in build/sync/bind; focus mode hard-codes its own allow-list.
- Several writes are *configure-authoritative* (dimension/vis), so "settings" can't be reasoned about independently of `configureLiveWidget`.

**Recommendation for new design**: extract a **`widgetSettingsService` submodule** owning the panel DOM contract, dropdown catalogs, state→UI sync, and a *declarative action/commit registry* (per widget type), so the per-type differences become data (which controls + which commit) rather than branching code. The actual data-shape commits (dimension/sequences/visualization/topN) should remain in the data/configure layer and be *referenced* by the registry, not absorbed into the settings service.

### Top surprises / complexity hotspots

- **No native form controls**: dropdowns are hand-rolled `div` menus with a `data-kdb-*` attribute contract and manual `.KDB_optionSelected`/`.KDB_visible` class toggling; selection sync is a separate pass from population. Heavy DOM bookkeeping.

- **Visibility gating is global** (`areSettingsButtonsHidden` toggles ALL gears), not per-widget — surprising if you expect per-widget control.

## RUN 4 — Slots / Binding / Live Filters (Layer B slots)

Scope read in full: `buildBindingPlan.js`, `applyBindingPlan.js`, `applyBindingPlanPostSuccess.js`, `buildSlotPlan.js`, `buildMirrorPatch.js`, `applyLiveWidgetSlots.js`, `applyLiveWidgetLocalFilters.js`, `applyLiveWidgetTopN.js`, `buildFilterBodyFromDescriptor.js`, `buildFilterDescriptors.js`, `applyHierarchyToHelperTable.js`, `claimTopNHelperTable.js`, `commitTopNChange.js`, `parseTopNOption.js`. ### The big picture: a declarative **compute → apply** binding pipeline (with legacy imperative twins)
`configureLiveWidget` (Run 1) is **compute-first/apply-second**. This layer is the heart of both halves:
- **COMPUTE (pure, no side effects)**: `buildBindingPlan` → `{buildSlotPlan, buildFilterDescriptors, buildMirrorPatch}` (+ `parseTopNOption`). Produces a single declarative **BindingPlan** object. No Cognos calls, no state writes.
- **APPLY (all side effects)**: `applyBindingPlan` → consumes the BindingPlan, performs ALL Cognos visible-widget mutations + render + the state mirror commit, with `applyBindingPlanPostSuccess` for non-critical writebacks and `buildFilterBodyFromDescriptor` turning descriptors into Cognos filter bodies.
- **TopN is computed earlier** (before `buildBindingPlan`) by `applyLiveWidgetTopN` (hidden helper-table query) and threaded into the plan as `helperTableResult` → `buildFilterDescriptors`.

**Crucial finding — duplication / dead-twin smell**: `applyLiveWidgetSlots` and `applyLiveWidgetLocalFilters` are **imperative, direct-Cognos-write twins** of the declarative `buildSlotPlan`+`applyBindingPlan(slot loop)` and `buildFilterDescriptors`+`buildFilterBodyFromDescriptor`+`applyBindingPlan(filter loop)` paths. The slot-id resolution helpers (`buildFinalSlotIds`, `resolveSlotColumnIds`, `resolveSeriesColumnIds`, `qualifyKennzahlValuesSlotId`, `cleanListDimensionId`, `shouldKeepDefaultAlongSelection`, `slotNamesFromVisConfig`, `slotIsRequired`…) are **near-verbatim copy-pasted** between `buildSlotPlan.js` and `applyLiveWidgetSlots.js`; the filter helpers (`resolveLocalFilterItemId`, `resolveFilterDescriptor`, `resolveKennzahlDefaultsBranchKey`, dimension include/exclude/reverse, `buildDimensionIncludeExcludeOrBody`) are copy-pasted between `applyLiveWidgetLocalFilters.js` and `buildFilterDescriptors.js`. The declarative BindingPlan path (`buildBindingPlan`→`applyBindingPlan`) is what `configureLiveWidget` actually drives (Run 1); `applyLiveWidgetSlots`/`applyLiveWidgetLocalFilters` look like **superseded legacy** kept around (no caller found in this scope). `applyLiveWidgetLocalFilters.resolveLocalFilterItemId` is still imported/used by `applyLiveWidgetTopN` for the aggregation-id lookup, so the module isn't fully dead.

### Binding plan pipeline: `buildBindingPlan` → `applyBindingPlan` → `applyBindingPlanPostSuccess`

**What a BindingPlan is** (shape documented atop `buildBindingPlan.js`): a pure declarative description of the intended live-widget binding —
```
BindingPlan {
  ok, error, reason,
  visualizationType: { label, cognosVisualizationTypeId },
  slotsChanged: boolean,
  slotsToClear: ["all"] | [],
  slotPlan: [{ slotName, columnIds, sortByColumn?, sortSpecs? }],
  filterDescriptors: [{ kind, mode, itemId, values, options? }],
  managedFilterItemIds: string[],
  mirrorPatch: { visualizationType, dimension, topN, topNResultValues,
                 topNExcludeItemId, datasourceId, datasourceName }
}
```
- **`buildBindingPlan(_KDB, widgetId, dataConfig, hierarchySnapshot, helperTableResult)`**: wraps the three builders. Injects `hierarchySnapshot` + `_KDB.properties.filterPropObj` into the slot-plan input, calls `buildSlotPlan` → `buildFilterDescriptors` → `buildMirrorPatch`, returns `createSuccess`/`createFailure`. Failure codes bubble up from the sub-builders (`buildSlotPlanFailed`, `missingDimensionSelectionAffects`, `buildFilterDescriptorsFailed`, `unknownTopNValue`, etc.). Pure + try/catch'd; never throws.
- **`slotsChanged` policy** (`resolveSlotsChanged` by lowercased `reason`): `topn`/`hierarchyfilter`/`hierarchy` → **false** (slots untouched, only filters re-applied); `visualizationtype`/`dimension`/`sequences` → **true**; default → **true**. `slotsToClear = ["all"]` iff `slotsChanged`. This is the key optimization: a topN or hierarchy change does NOT clear/rebuild slots, only filters.

- **`applyBindingPlan(_KDB, widgetId, plan, mySeq, options)`** (async) — owns every visible-widget Cognos write, in strict order, **re-checking `isBindingSequenceCurrent(_KDB,id,mySeq)` before/after every await** (returns `{superseded:true}` and bails on a newer sequence — superseded is never treated as failure):
  1. `getVisType(id)` (read current).
  2. `setVizDataSource(mirrorPatch.datasourceId, id)`.
  3. `setVisType(desiredCanonicalVisType, id)` — only if current canonical ≠ desired (canonicalized via a lowercase map: line/pie/list/stackedbar/stackedcolumn).
  4. **If `plan.slotsChanged`**: `clearAllSlots(id)` → `clearAllLocalFilters(id)` (validates result truthy/`ok!==false`) → `setVizDataSource` **again** (re-set after clear).
  5. **Slot loop** per `slotPlan`: `addDataItemsToSlot(id, slotName, columnIds)` then `sortDataItemInSlot(slotName, columnId, order, id, priority)` per resolved sort spec (`resolveSortSpecs`: supports `sortSpecs[]` or legacy single `sortByColumn`).
  6. `removeManagedFilters(_KDB, id)` (drops the previous configure pass's managed local filters).
  7. **Filter loop** per `filterDescriptors`: `buildFilterBodyFromDescriptor` → if body, `addOrReplaceLocalFilter(id, descriptor.itemId, body)` → `rememberManagedKey(_KDB, id, itemId)`.
  8. `renderWidgetCycle(_KDB, id, {reason, isHistoryReplay:false, waitForStart:true})` (Run 1 render engine — **this is who triggers render after configure**, answering a Run-1 open question).
  9. **Only on render success + current sequence**: `mergeSettings(_KDB, id, mirrorPatch)` (the state mirror commit), `setLastConfirmedBindingPlan(_KDB, id, plan)` (unless replay pass), then `applyBindingPlanPostSuccess`.
- Returns `{ok, superseded, error, replayed}`.

- **Apply-failure handling (`handleApplyFailure`, "Gate 8 inline replay")**: on any apply error (and not a replay pass), it tries to **roll back to the last good binding**: `peekEntry().lastConfirmedBindingPlan`; if present and `!sameBindingPlan(lastPlan, plan)`, it re-invokes `applyBindingPlan(..., {isReplayPass:true})` with that last plan. If the replay succeeds → marks `lastConfigureFailure="apply-failed-rolledBack"` + diagnostic `{ok:false, replayed:true}` and returns `{ok:false, replayed:true}` (widget shows last-good state, not error). Otherwise `enterErrorState`: `setLifecycle("error")` + `setLastConfigureFailure(code)` + `setConfigureDiagnosticSummary({ok:false})` + emit `WIDGET_RESCAN_REQUESTED{reason:"applyFailure"}` (recovery deferred to rescan/recover gates, Run 1).

- **`applyBindingPlanPostSuccess(_KDB, id, plan, mySeq)`**: best-effort, sequence-guarded, never breaks confirmed state. Two writebacks: (a) **list-summary suppression** — if the vis is a List, `cognosAPI.setTableSummaryValue(true, id)` immediately + again after a 300 ms `setTimeout`; (b) **visualization title** — `setTitle(id, buildVisualizationTitle(_KDB,id))`. Both wrapped in their own try/catch with warning logs.

### Slot plan: `buildSlotPlan`, `buildMirrorPatch`, `applyLiveWidgetSlots`
- **Slot model** (`SLOT_KEYS`): `values, categories, series, color, repeatHorizontal, repeatVertical, grid_cols`. `REQUIRED_SLOTS = {values, categories, series, grid_cols}` (an empty required slot → `requiredSlotEmpty`, unless raw config is `"noTable"` or the "none" rule applied). Pie-family vis labels (`pie/donut/doughnut/treemap`) route the hierarchy item to `repeatVertical`.
- **`buildSlotPlan(dataConfig)`** (pure; "mirrors `applyLiveWidgetSlots` without Cognos calls"): derives active slot names from `visTypeConfig` (a key is active if present + non-empty) plus the dimension-affected slot. For each slot, `buildFinalSlotIds` resolves `columnIds` from:
  - **default ids**: `slotRawConfigForCode` (per-`kennzahlCode` object override), `replaceKennzahlPlaceholder` (`replaceKennzahlName`→code), and for the `values` slot `qualifyKennzahlValuesSlotId` (appends `.[<code>]` to a `[KDB Kennzahlen]` measure root). `series` is special (`resolveSeriesColumnIds`: uses the selected dimension itemId when `dimensionSelectionAffects==="series"`).
  - **selection overlay**: `dimensionSelectionAffects` / `sequencesSelectionAffects` tokens decide which slot a dimension/sequence selection feeds. `none`→clears (the "none rule"), default→defaults, otherwise the selected dimension/sequence itemIds (from `dataTableConfig.dimensions[dim].itemId` / `.sequences[seq].itemId`), with `shouldKeepDefaultAlongSelection` deciding whether defaults are appended.
  - **list/pie specials**: list `grid_cols` reorders (`reorderListGridCols`: moves first selected dim item behind two base columns) and uses up-to-2 sort specs; pie `categories` override (`applyPieCategorySelectionOverride`); `ensureRepeatHorizontalSlot`.
  - **hierarchy merge**: `resolveHierarchySlotItemId` (from `hierarchySnapshot.activeDownstreamName` + `resolution.hasConfirmedSelection`, resolved via `filterPropObj` source-key matching + `rewriteUniqueNameSourceToken`) is merged into the affected slot (`mergeHierarchyIntoAffectedSlot`) or, for lists, woven into `grid_cols` (`mergeHierarchyIntoListGridCols`).
  - Sort metadata via `applySortMetadata` (from `dataTableConfig.sorting`): list grid → `sortSpecs[]` (first 2 cols), else single `sortByColumn`.
  - Hard failures: `missingDimensionSelectionAffects`, `missingSequencesSelectionAffects`, `missingSelectedDimensionItemId`, `missingSelectedSequenceItemId`, `requiredSlotEmpty`.
- **`buildMirrorPatch(_KDB, dataConfig, filterBuildResult)`**: the post-apply settings mirror. Normalizes `dimension` (default `"default"`), parses topN (`parseTopNOption`); if dimension default OR topN default → `topN:"default"` and `topNResultValues/topNExcludeItemId` left undefined; else carries `topN` ("top-N"), and `topNResultValues`/`topNExcludeItemId` **from the helper result** (`filterBuildResult`). Also mirrors `visualizationType, datasourceId, datasourceName`. This is the exact patch `applyBindingPlan` merges into `_KDB.state.widgets[id].settings` only after render success.
- **`applyLiveWidgetSlots(_KDB, widgetId, dataConfig)`** (imperative legacy twin): synchronously `clearAllSlots` then for each slot `addDataItemsToSlot` + `applySortingForSlot` (`sortDataItemInSlot`) + list `moveDataItemInSlot("grid_cols",0,2,id)`. Same slot-resolution logic as `buildSlotPlan`, but writes directly to Cognos and returns `{ok, appliedSlots[], error, slotName, …}`. **No sequence guard, no plan object** — the declarative path superseded it.

### Live local filters: `applyLiveWidgetLocalFilters`, `buildFilterDescriptors`, `buildFilterBodyFromDescriptor`
- **Filter sources (3, in order)** — same in both the imperative and declarative paths:
  1. **`visTypeConfig.widgetFilter`** map: each key resolved to an itemId via `resolveLocalFilterItemId` — a `[`-prefixed key is a literal TM1 bracketed id; otherwise it MUST resolve through `_KDB.properties.parameterMappingObj["<key>_widget_localfilter_KID"]` or the whole configure fails with `missingParameterMapping` (Gate: no literal Cognos ids allowed). Value shapes: `{exclude|include|reverse|values:…}`.
  2. **Kennzahl-type defaults** (`kennzahlDefaults`): branch selected by `visPropBucketKey` → `Line`/`List`/`com.ibm.vis.custom.prognoseyearlinechart`/`allOther`; applies `branch.filter[itemId]` specs.
  3. **Dimension scoped filters** (`dataTableConfig.dimensions[dim]`): `include`/`exclude`/`reverse`; if include+exclude share the same itemId with values, a combined **include-OR-not-exclude** body (`buildDimensionIncludeExcludeOrBody` / `mode:"includeExcludeOr"`).
- **`applyLiveWidgetLocalFilters`** (imperative): `removeManagedFilters` then applies all 3 sources directly via `cognosAPI.addOrReplaceLocalFilter` (+ `buildKeepexcludeConditionsFilterObj` for excludes), tracking `rememberManagedKey`. Returns `{ok, applied[], skipped[]}` or `{ok:false, error:"missingParameterMapping", key, mapKey}`. Exposes `removeManagedFilters` + `resolveLocalFilterItemId` statics (the latter reused by `applyLiveWidgetTopN`).
- **`buildFilterDescriptors`** (declarative twin, pure): produces `filterDescriptors[]` with `{kind: widgetFilter|kennzahlDefault|dimension|topN|hierarchy, mode, itemId, values, options}`, `managedFilterItemIds[]`, and `topNResultValues`/`topNExcludeItemId`.
  - **TopN descriptor** (`buildTopNDescriptor`): from `helperTableResult` (the `applyLiveWidgetTopN` output) — `include` filter on the exclude-item with the helper-derived top-N values; failure codes `unknownTopNValue`, `missingTopNHelperResult`, `topNHelperFailed`.
  - **Hierarchy descriptor** (`buildHierarchyDescriptor`): from `hierarchySnapshot.resolution.downstreamValues`/`dominantValues`, source-key matched in `filterPropObj`, `rewriteUniqueNameSourceToken` + `rewriteValueArrSourceToken` + `sanitizeWidgetDownstreamDisplayValues`, emitted as `kind:"hierarchy"` `shape:"hierarchyKeepexclude"`. Failures `missingHierarchyValues/SourceConfig/ItemId`.
- **`buildFilterBodyFromDescriptor(_KDB, descriptor)`** (apply-phase translator): descriptor → Cognos local-filter body. Hierarchy → `{exclude:false, values, overrideHierarchyDefaultSelection:true, action:"keepexclude"}`; `includeexcludeor` → `conditionsInfo.conditions.or[...]` clauses; `exclude` → `buildKeepexcludeConditionsFilterObj`; `reverse`/default → `{values}`. **Throws `unknownFilterDescriptorMode`** for unrecognized modes (caught + re-coded by `applyBindingPlan`).

### Top surprises / complexity hotspots
- **Two complete, near-duplicated implementations** of slot + local-filter application (declarative BindingPlan path vs imperative `applyLiveWidgetSlots`/`applyLiveWidgetLocalFilters`), with copy-pasted resolution helpers. - **`slotsChanged` reason policy is subtle**: topN/hierarchy changes deliberately skip slot clear/rebuild (filters-only), while dimension/sequences/visType rebuild slots — easy to get wrong and cause stale slots or needless re-renders.
- **Gate-8 inline rollback** (`handleApplyFailure` re-applying `lastConfirmedBindingPlan`) is a hand-rolled transactional compensation: an apply failure silently reverts the visible widget to its last-good binding instead of erroring, unless the failed plan IS the last-good one. - **Pervasive `isBindingSequenceCurrent` re-checks** (every await boundary in `applyBindingPlan` and `applyLiveWidgetTopN`) — superseded is a first-class non-failure outcome. Reimplementation must preserve the "superseded ≠ error" distinction or it will spuriously error widgets during rapid reconfigure.

### Text widget — the contenteditable model
The text widget wraps a **Summernote-style editor** (`.note-editable`). All text behaviors re-resolve the live DOM per action because Cognos can rerender innards.

- **`resolveTextWidgetEditableNode(_KDB, widgetId, widgetEl?)`** — the single DOM resolver every text action calls. Looks up the widget element (`document.getElementById(id)`), then finds `editableEl` = `.textFillNoScroll .note-editable` ‖ `.note-editable` ‖ (fallback) `#<id>Editable` if contained. Derives `paragraphEl` = `editableEl > p`, `spanEl` = `editableEl > span`. Returns `{ editableEl, paragraphEl, spanEl, textNodeForFont (= span ‖ p ‖ editable), widgetEl }`. **`textNodeForFont` is the font-size target; `paragraphEl` is the text-content target.** Pure, no writes.
- **`startTextWidgetTextEdit(_KDB, id, widgetEl?, options?)`** — inline-edit lifecycle. Gate: `entry.lifecycle === "active"` && `widgetType === "text"` && `editableEl` present. Idempotent re-entry guard via attribute `data-kdb-text-edit-active="1"` (re-focus if already editing). On start: snapshots `originalText` (from `readEditableText` = paragraph/editable `textContent`), sets `data-kdb-text-edit-active="1"`, sets `contenteditable="true"`, focuses, selects all content (`selectEditableText` via `document.createRange` + `getSelection`, unless `options.selectText === false`), then **arms listeners after a 0ms `setTimeout`** (`FOCUS_ARM_DELAY_MS`, so the initial focus doesn't immediately commit). Listeners: `focusout` → `commitFromDom`, `keydown` Escape → `cancelEdit`. `commitFromDom` (one-shot via `didFinish`) re-resolves, reads next text, cleans up, then `Promise.resolve(commitWidgetTextEdit(_KDB,id,nextText,{}))` and on `ok` re-fits automatic font (`refitAutomaticFontSize`). `cancelEdit` writes back `originalText` (no commit). `cleanup` clears the arm timer, removes both listeners, sets `contenteditable="false"`, removes the active attribute. **No state written here directly** — the actual `settings.text` write + history is in `commitWidgetTextEdit` (run 3, key `widget_textEdit`). Note: started via the settings panel's 50ms-deferred `scheduleTextEditStart` (run 3).
- **Font size** (`applyTextWidgetFontSize` + `commitTextWidgetFontSizeChange`):
  - `applyTextWidgetFontSize(_KDB, id, value, options?)` applies to `resolved.textNodeForFont`. `normalizeFontSizeValue` maps via `dropdownOptions.hardcoded.fontSize` (key or value match), strips trailing `;`, collapses `""`/`default`/`automatic` → `"automatic"`, coerces `"<n>"`/`"<n>px"` → `"<n>px"`. **Automatic mode** adds class `responsiveFontSize` and schedules an auto-fit: `scheduleFontFit` → `findOptimalFontSize` does a **binary search (1–200px, `FONT_FIT_DELAY_MS=50` per step) using `doesTextOverflow`** (compares `target.scroll{Width,Height}` vs the box `client/offsetWidth/Height`), settling on the largest non-overflowing size and removing the `overflow` prop. Explicit mode removes the class and sets `style.fontSize` directly. Statics: `normalizeFontSizeValue`, `isAutomaticFontSize`.
  - `commitTextWidgetFontSizeChange(_KDB, id, value, options?)` — gate active+text. Snapshots `beforeFontSize`, normalizes, `markPending("fontSize", true)`, writes **`settings.fontSize`** via `setWidgetSetting`, applies to DOM; on apply failure **rolls back** the setting (deletes if previously empty) and clears pending. On success emits `WIDGET_CONFIGURATION_CHANGED {action:"fontSize"}` + `WIDGET_CLEANUP_REQUESTED`. **Intentionally pushes NO history** (comment: "Font-size history is intentionally left out of this phase") — this is the one settings commit with no history step.
- **`applyTextWidgetRestyle(_KDB, id, restyleValue)`** — text "restyle" (= the `layout` setting for text) is **pure CSS chrome, not a Cognos layout**. Resolves a class from `dropdownOptions.hardcoded.restyle`, removes any existing `KDB_widgetHeader*`-prefixed class, adds the selected class. Returns boolean. (This is what `commitWidgetLayoutChange`'s text path calls — run 2.)
- **`cleanTextWidgetForTransfer(_KDB, elOrId)`** (async) — pre-launchpad teardown. Calls shared `cleanLaunchpadWidget(_KDB, el‖id)`, then `teardownWidgetState`: iterates `entry.listeners[*]` and `entry.subscriptions[*]` and disposes each via a **polymorphic `teardownHandle`** (tries, in order, `fn()` / `.abort()` / `.unsubscribe()` / `.disconnect()` / `.remove()` / `.off()`), then `delete`s both maps. (Same runtime-handle disposal contract as the live path in run 1's `resetWidgetToLaunchpad`.)
- **`sendTextWidgetToLaunchpad(_KDB, widgetSource, resolvedMeta?)`** (async) — resolves meta (`resolveLiveWidgetMeta`), `ensureEntry`. **Bails (and forces `lifecycle="active"`) unless ALL hold**: meta is a `WIDGET.TEXT`, has an el, is not the host widget (`_KDB.elements.widgetEl`), `properties.KDBHideWidgetsToggle === true`, and tab is not a launchpad helper tab. Classifies pad (`classifyLiveWidgetLaunchpadPad`); if `padKey === "text"`, `cleanTextWidgetForTransfer` first. Appends to the launchpad slot (`appendWidgetToLaunchpadSlot`); on success `setLaunchpadPlacement` (`launchpadSlot = "text_" + childIndex`, `widgetType:"text"`) and emits `WIDGET_SENT_TO_LAUNCHPAD`.
- **`takeTextWidgetFromLaunchpad(_KDB, request, options?)`** (async) — the text sibling of the live take. Resolves widgetId (from `widgetId`/`widgetEl`/`widgetSource`), `padKey` (only ever `"text"`, else null/abort), tabId (request → state → current tab → first launchpad tab). Finds slot meta/el (`findLaunchpadSlotMeta` + `_KDB.elements.launchpadSlot`). **Race-safe claim** via DOM attribute `data-kdb-claimed-run=<runId>` (`runId` from options/request/`launchpad.restoreRunId`/"default") — `findCandidate` skips already-claimed children and prefers the requested id. Removes from slot (`removeWidgetFromLaunchpadSlot`), `cleanTextWidgetForTransfer`, releases the claim, then `setLifecycle("loading", {tabId, widgetType:"text"})` + `markPending("drop", true)`. Emits `WIDGET_TAKEN_FROM_LAUNCHPAD` + `WIDGET_DROPPED` (`widgetType:"WIDGET.TEXT"`) unless `suppressSuccessEvents` (the drop path suppresses, run 1). Returns `{padKey, tabId, widgetEl, widgetId, launchpadSlot:"text"}`.

### Launchpad routing model (how a live widget moves to/from a pad)
**Pad taxonomy** — there are exactly **5 launchpad pad keys**: `visualization`, `text`, `dataTables`, `shapes` (and `live` is only an *alias* that maps to `visualization` on the take side). Pads are physical DOM slots, not per-widget; resolved via `_KDB.state.launchpad.padsByKey[padKey]` (a list of slot-metas keyed by `tabId`/`aliases`) + `_KDB.elements.launchpadSlot(padKey, childIndex)` for the actual DOM container.

- **`classifyLiveWidgetLaunchpadPad(_KDBOrWidgetMeta, _widgetMeta?)`** — pure pad classifier (accepts either `(meta)` or `(KDB, meta)` via `resolveArgs`; needs `_KDB` only to read `properties.loadingTablesPropObj`). Decision order (first match wins):
  1. `visualType ∈ SPECIAL_VIS_TYPES` (`COM.IBM.VIS.CUSTOM.PROGNOSEYEARLINECHART`) → **`shapes`**.
  2. `visualType === "LIST"` AND `visualTitle` is in the runtime loading-table names (`collectLoadingTablesPropObj`, normalized lowercase) → **`shapes`** (these LIST tables are infra helpers, not user datatables).
  3. `visualType === "LIST"` AND `visualTitle ∈ SPECIAL_LIST_TITLES` (a hardcoded 19-entry denylist: `helptable`, `personal_sichten`, `leitung*`, `superuser`, `dienststelle_*hierarchy/default`, `sichten_*`, `alle`, `personengruppe`, `personal_kdbready`, …) → **`shapes`**.
  4. `widgetType === "WIDGET.SHAPE"` → **`shapes`**.
  5. `widgetType === "WIDGET.TEXT"` → **`text`**.
  6. `visualType === "LIST"` (any remaining list) → **`dataTables`**.
  7. `visualType ∈ CHART_TYPES` (`BAR, STACKEDBAR, COLUMN, STACKEDCOLUMN, LINE, PIE`) → **`visualization`**.
  8. **fallback** → **`shapes`** (anything unrecognized is parked in shapes).
- **`resolveLiveWidgetMeta(_KDB, widgetSource)`** (async) — the meta resolver used by send + routeAll. Resolves `widgetId` (string ‖ DOM `.id` ‖ `getId()` ‖ `.widgetId`), then `await cognosAPI.getWidgetWhenReady(id)` (best-effort), normalizes `widgetType` (`LIVE→WIDGET.LIVE`, `TEXT→WIDGET.TEXT`, `SHAPE→WIDGET.SHAPE`; resolution chain: source `getType` → api `getType` → `cognosAPI.getType(id)`). **Only when live** (`isLiveType` = exactly `WIDGET.LIVE` or `WIDGET.LIVE*`) does it read `cognosAPI.getVisType(id)` + `getVisTitle(id)`. Returns `{isLiveWidget, tabId, visualTitle, visualType, widgetEl (= document.getElementById(id)), widgetId, widgetType}`. Pure read — no state writes, all Cognos calls try/caught to empty string.
- **`sendLiveWidgetToLaunchpad(_KDB, widgetSource, resolvedMeta?)`** (async) — the send path. Sequence:
  1. Resolve meta (reuse `resolvedMeta` or `resolveLiveWidgetMeta`). Abort (`false`) if no `widgetId`.
  2. `ensureWidgetState` = `setWidgetSetting.ensureEntry(_KDB, widgetId)`.
  3. **Four bail-gates**, each forcing `setLifecycle(id, "active")` then returning `false`: (a) not a live widget / no el / **is the host widget** (`_KDB.elements.widgetEl` self-or-ancestor-or-descendant check), (b) `properties.KDBHideWidgetsToggle !== true` (the global "hide widgets to launchpad" master switch — same precondition as the text send in run 5), (c) `tabId` is a launchpad **helper tab** (`_KDB.state.launchpad.helperTabIds`).

  5. **Pre-transfer clean** only for `visualization` or `dataTables` pads (`shouldCleanLiveWidgetForPad`) → `await cleanLiveWidgetForTransfer(_KDB, widgetEl)`. (shapes/text live widgets are NOT vis-cleaned.)
  6. `appendWidgetToLaunchpadSlot(_KDB, {padKey, tabId, widgetEl})` — DOM `slotEl.appendChild` + parent-verify. On null → bail with `lifecycle="active"`, `false`.

The `launchpadSlot` string format `"<padKey>_<childIndex>"` is the round-trip key consumed by the take side.
- **`takeLiveWidgetFromLaunchpad(_KDB, request, options?)`** (async) — the inverse. Sequence:
  1. `resolveRequestedWidgetId` (from `widgetId` / `widgetEl` / `widgetSource` el-or-string).

  4. `findLaunchpadSlotMeta(padKey, tabId)` + `_KDB.elements.launchpadSlot(padKey, childIndex)` → `slotEl`. Abort `null` if pad/tab/slot missing.
  5. **Race-safe claim**: `runId` from `options.runId` ‖ `request.runId` ‖ `_KDB.state.launchpad.restoreRunId` ‖ `"default"`. `findCandidate` scans `slotEl.children`, skipping any with a *different* `data-kdb-claimed-run` and preferring the requested id (with a second pass that returns the exact id even if claimed). `claimCandidate` sets the attr; `releaseCandidateClaim` clears it (only if it still matches the runId).
  6. `removeWidgetFromLaunchpadSlot(_KDB, {padKey, tabId, widgetEl: candidate})` — on fail, release claim, abort.
  7. `await cleanLiveWidgetForTransfer(_KDB, candidate)` (wrapped; on throw release+abort), then release claim.

  9. Unless `options.suppressSuccessEvents === true` (the run-1 drop path suppresses), emit `WIDGET_TAKEN_FROM_LAUNCHPAD` + `WIDGET_DROPPED` (`widgetType:"WIDGET.LIVE"`). Returns `{padKey, tabId, widgetEl, widgetId, launchpadSlot: padKey}`.

## RUN 6b — topN core + state

Scope: the 16 *pure-logic* + *state-transition* modules under `…/canvas/widgets/live/topN/core/*` and `…/topN/state/*`. These are the **"resolution brain"** of topN. They perform **no Cognos calls and no DOM work** — they interpret config/snapshot inputs into declarative *plans* and *descriptors*, and they own a small **serializable resolution state machine**. The Cognos-touching wrappers (`api/*`), the orchestrating `actions/resolveTopNResolution`, and the `events/*` pub-sub are explicitly **run 7** (only peeked here). The orchestrator entry (`__topNOrchestrator__`) was **run 6a**. Helper-table claim/cleanup lives in run 4/7.

### Big picture: what topN *is* and the two-widget dance
A topN-configured widget is a **visualization (chart) widget in a special mode**. To compute "the top-N members of dimension X by measure Y" KDB3 cannot ask the visible chart directly — instead it spins up a **hidden helper LIST table** (the "helper widget", routed to the `shapes`/`dataTables-slot` pad per run 4/5) whose flat query result yields the N member *display values*. Those values are then written back to the **visible** widget as a `topN` local filter (a `mode:"include"` filter on the dimension's *exclude* item id). The run-6b modules are the pure pieces that: decide **whether** a helper resolution is needed (`resolveResolutionRequirement`), **build the helper-table query plan** (`buildHelperPlan` + `resolveJahrPlan` + `resolveHierarchyHelperPlan`), **extract** the values from the helper's flat data (`extractFlatData`), **build the visible-widget filter descriptor** (`buildTopNDescriptor`), and **track the async lifecycle** so a late/stale resolution can't clobber a newer one (`state/*` + `checkStaleGuard`).

### TopN resolution STATE MACHINE (`state/{start,update,finish,cancel,read}`)
- **Where it lives**: `_KDB.state.widgets[<widgetId>].pending.topNResolution` — i.e. it is a **per-widget** entry under that widget's shared `pending.*` substate (the same `pending` bag that holds `binding`, `drop`, `configureManagedFilterItemIds`, etc., per `setWidgetSetting`). All writes go through `setWidgetSetting.markPending(_KDB, widgetId, "topNResolution", resolution)` and clears through `setWidgetSetting.clearPending(_KDB, widgetId, "topNResolution")`. **Keyed strictly by visible `widgetId`** (`widgetId || visibleWidgetId`, string-normalized). One in-flight resolution per widget.
- **Record shape** (created by `startTopNResolution`):
  ```
  {
    lifecycle: "pending" | "error",      // success => record deleted, not a status
    sequenceId: "topN-<startedAt>-<counter>",  // runtime-only monotonic id
    helperWidgetId: <id> | null,
    requestedTopN: <raw topN value> | null,
    source: <string> | null,             // e.g. "configureLiveWidget"
    reason: <string> | null,
    startedAt, updatedAt, finishedAt,    // Date.now() millis
    error: <string> | null,
    isSuperseded: false,
    cleanupPlan: { filterItemIds:[], clearSlots:[], releaseClaim:bool } | null,
    topNExcludeItemId: <id> | null       // merged in via update patch
  }
  ```
- **Lifecycle / status values**: only two persisted: `"pending"` (in-flight, the *current async owner*) and `"error"` (a failed terminal record kept for diagnostics). **There is no `"done"` status — success deletes the key entirely.** `readTopNResolution` treats *only* `lifecycle === "pending"` as a live owner (`isPending`).
- **`sequenceId` / staleness**: generated by a module-level `sequenceCounter` (process-monotonic) as `"topN-" + timestamp + "-" + counter`. It is **runtime-only / not stably serialized** (resets per page load). Every mutating transition reads current state via `readTopNResolution(_KDB, widgetId, sequenceId)` and computes `isCurrent = isPending && (!expectedSequenceId || resolution.sequenceId === expectedSequenceId)`. A non-matching incoming sequence → reject with `{ok:false, error:"staleTopNResolution", superseded:true}` **without writing**.
- **Transitions**:
  - `start` — writes a fresh `pending` record (mints `sequenceId` unless caller supplies one). Returns `{ok, resolution}`.
  - `update` — merges a **sanitized** patch (only `helperWidgetId`, `cleanupPlan`, `topNExcludeItemId` are allowed through `sanitizePatch`) into the current record, **forcing `lifecycle:"pending"` and preserving the original `sequenceId`**, bumps `updatedAt`. Rejects if `!isCurrent`.
  - `finish` — if `!isCurrent` → stale/superseded reject. If `source.ok === true` → `clearPending` (success = delete, returns `{ok:true, cleared:true}`). If `ok !== true` → rewrites record to `lifecycle:"error"` with `error`, `finishedAt`, `isSuperseded:false`, and **keeps it** (markPending) so the error is visible.
  - `cancel` — if not pending → treat as success no-op. If a sequenceId is supplied and not current → stale reject (`superseded:true`). Else `clearPending` and return the prior `helperWidgetId` + `cleanupPlan` to the caller, plus `reason` (default `"cancelled"`). **Claim release is explicitly NOT done here** — comment notes it's left to the caller (run 6a `cleanupWidget` does `releaseTopNHelperClaim` separately).
  - `read` — pure, no mutation; deep-clones the resolution + cleanupPlan and reports `isPending`/`isCurrent`/`sequenceId`/`helperWidgetId`/`cleanupPlan`.
- All four mutators are wrapped in try/catch returning typed failures (`topNResolution{Start,Update,Finish,Cancel}Failed`).

### TopN DESCRIPTOR (`buildTopNDescriptor`) + `parseTopNOption`
- **`parseTopNOption(raw, topNOptions)`** — the single source of truth for the top/bottom/N contract. Returns one of:
  - `{kind:"default"}` for `null`/`undefined` or the sentinels `"" | "default" | "none"`;
  - `{kind:"count", n, value, key}` when the **normalized key** exists in the caller-supplied `topNOptions` map (the map provides `key → n`);
  - `{kind:"unknown", value}` otherwise.
  - **Normalization** (`normalizeTopNKey`): lowercases+trims, and a regex `^top\s*-?\s*(\d+)$` collapses legacy `"top2"`, `"top 2"`, `"Top-2"`, `"top - 2"` → canonical `"top-2"`. **It does NOT itself know the numeric `n`** — `n` comes from the `topNOptions` map lookup, so the dropdown option table is the authority on what each key means. (No explicit "bottom" handling appears in these pure modules — the top/bottom distinction must be encoded in the option map keys/values upstream.)
- **`buildTopNDescriptor(input)`** — turns helper output into the visible-widget local-filter descriptor:
  - `parsedTopN.kind === "unknown"` → `{ok:false, error:"unknownTopNValue"}`.
  - default dimension OR `parsedTopN.kind === "default"` → **clear path**: `{ok:true, descriptor:null, topNResultValues:undefined, topNExcludeItemId:undefined}` (topN turned off).
  - else requires a `helperResult`; missing → `missingTopNHelperResult`; `helperResult.ok === false` → propagate its error.
  - extracts `values = helperResult.topNResultValues || .values` (trimmed, non-empty) and `excludeItemId = helperResult.topNExcludeItemId || .excludeItemId || dimEntry.exclude.itemId` fallback. **Active topN with no values OR no excludeItemId → `missingTopNHelperResult`** (the file comment: "Active TopN never succeeds without values and an exclude item id").
  - **Descriptor shape**: `{kind:"topN", mode:"include", itemId:<excludeItemId>, values:[…members…], options:{source:"helperTable", n:<count>}}`, plus echoed `topNResultValues` + `topNExcludeItemId`. **Note the inversion**: the filter is `mode:"include"` keyed on the dimension's *exclude* item id — it keeps exactly the N computed members.

### PLANNERS (`buildHelperPlan`, `resolveJahrPlan`, `resolveHierarchyHelperPlan`, `resolveResolutionRequirement`)
- A **"helper plan"** = a declarative, Cognos-free description of how to set up the hidden helper LIST query and how to tear it down. `buildHelperPlan` returns:
  ```
  { ok, error,
    slotPlan: [{ slotId:"grid_cols", itemIds:[jahrColumnId?, topNItemId, valuesColumnId] }],
    helperFilters: [ dimensionExclude, aggregation, jahr?, hierarchy? ],
    topBottom: { slotId:"grid_cols", n, sortValueItemId:valuesColumnId },
    resultExcludeItemId,
    cleanupPlan: { filterItemIds:[…], clearSlots:["grid_cols"], releaseClaim:false } }
  ```
  - Hardcoded domain constants: helper slot `"grid_cols"`; default exclude values `["Gesamt","ALLE","^"]`; an **aggregation pin** `AggregationstypId = "Monatsdurchschnitt"` (always added as an `include` filter). The dimension-exclude filter uses `operator:"endswith", ignoreCase:true, valueType:"display"`.
  - `valuesColumnId` resolution (`resolveValuesColumnId`/`normalizeValuesColumnId`): falls back to `kennzahlCode` when `visTypeConfig.values` is `"noTable"`/empty; supports a `replaceKennzahlName` template token and appends `.[<code>]` to a `[`-prefixed unique name when needed.
  - Fails fast with `missingTopNCount` / `missingTopNOrExcludeItemId` / `missingValuesColumnForTopN`.
- **`resolveResolutionRequirement`** — the **gatekeeper**: "does this binding need a helper resolution?" Returns `requiresHelperResolution:true` **only** for `kind:"count"` topN on a **non-default dimension**. Short-circuits: unknown topN → `ok:false`; default dimension → `defaultDimension`; default topN → `defaultTopN`. It also implements the **stored-values shortcut**: when `useStoredTopNValues === true` (or a history replay with stored values + non-default topN/dimension), it returns `requiresTopNValues:true, requiresHelperResolution:false, canUseStoredTopNValues:true` and echoes the stored `topNResultValues` + `topNExcludeItemId` (so no helper query is spun up). Missing stored values/exclude → `missingStoredTopNValues` / `missingStoredTopNExcludeItemId`.
- **`resolveJahrPlan`** — builds an optional **year ("Jahr") pin** for the helper query. Discovers a `jahrColumnId` by scanning `properties.listPropObj[source].grid_cols` and `stackedBarPropObj[source].categories` for a column whose name contains `"jahr"`. If there is **no active Jahr page-context** (`hasActiveContext`), it picks a **default Jahr value** from `tablesByName` (first jahr-named column's first display/use value) and emits a `{kind:"jahr", mode:"include", itemId:jahrColumnId, values:[defaultJahrValue]}` helper filter + `cleanupItemIds:[jahrColumnId]`. This pins the helper to a single year so the top-N isn't summed across all years. Pure interpretation; caller provides `pageContextItems`/`tablesByName`.
- **`resolveHierarchyHelperPlan`** — builds an optional **hierarchy include filter** so the helper query respects an active downstream hierarchy selection. Requires `hierarchySnapshot.resolution.hasConfirmedSelection === true` and an `activeDownstreamName`; else **skip** (`applied:false`). Picks canonical values (`downstreamValues` ‖ `dominantValues`), resolves the source/filter config from `filterPropObj` (exact then fuzzy `_TM1`-stripped match on datasourceName/Id/kennzahlenTable), pulls `itemId`, **rewrites the source token** to the target datasource (`[<target>_TM1]…`), and emits `{kind:"hierarchy", mode:"include", itemId, values, options:{overrideHierarchyDefaultSelection:true, action:"keepexclude"}}` + `cleanupItemIds:[itemId, itemId+"_1"]`. Failure reasons: `missingHierarchyValues`/`missingHierarchySourceConfig`/`missingHierarchyItemId`.

### HIERARCHY REWRITE (`rewriteHierarchyValues` + `extractFlatData`)
- **The topN-on-hierarchy problem**: hierarchy member unique-names embed a **source/datasource token** as their first bracketed segment (`[SourceName]…`) and display values may carry a `#`-prefixed code per `" | "`-delimited token. The *visible* widget's datasource differs from the canonical hierarchy snapshot's, so the values must be **retokenized to the helper's target datasource** before they're valid as a helper-query filter.
- **`rewriteHierarchyValues(values, targetSourceToken)`** (pure, used by the hierarchy planner): for each value object, (1) rewrites `value.u`'s leading `[token]` → `[<target>_TM1]` (appends `_TM1` if absent), and (2) sanitizes `value.d` via `stripHashPrefixPerToken` — splits on a spaced-pipe delimiter (`\s|\s`, incl. NBSP/figure/narrow spaces) and strips everything up to and including each `#`, rejoining with `" | "`. So `"AB#Berlin | CD#Mitte"` → `"Berlin | Mitte"`.
- **`extractFlatData(flatData, parsedTopN)`** — reads the helper LIST's already-fetched flat data and returns the top-N display values. Expects `flatData.columnDataObjArray` (rows) + `flatData.colKeys`. **Picks the dimension column as `colKeys[1]` when ≥2 keys else `colKeys[0]`** (assumes col[0] is the value/sort column and col[1] the dimension). Takes the first `n` rows' value at that key (trimmed, non-empty). Guards: empty rows/keys → `emptyTopNQueryResult`; **stale-label guard** → if any colKey lowercases to `"superuser"` or `"dbversion"` → `staleHelperQueryResult` (these labels indicate the query returned a login/version placeholder instead of data); `n<1` → `missingTopNCount`.

### GUARDS & HISTORY (`checkStaleGuard`, `decideHistoryPush`, `buildMirrorPatch`)
- **`checkStaleGuard(input)`** — the *boundary* staleness check (distinct from the state machine's internal `isCurrent`). Given a `widgetEntry` + `incomingSequenceId`: removed/missing widget → `{isCurrent:false, isSuperseded:false, reason:"visibleWidgetRemoved"}`; no incoming sequence → accept; sequence mismatch → `{isCurrent:false, isSuperseded:true, reason:"staleBindingSequence"}`; match → accept. It **resolves the "current" sequence from either `pending.topNResolution.sequenceId` or `pending.binding.seq`** — preferring the topN sequence when the incoming id matches it or starts with `"topN-"`. So it unifies the topN-resolution sequence and the generic binding sequence into one staleness decision.
- **`decideHistoryPush(input)`** — pure gate for whether a *committed* topN change pushes app history (`historyKey:"widget_liveTopNChange"`). `shouldPush:true` only when **all** hold: parsed topN not `unknown`; `result.ok === true`; not `superseded`; not `options.skipHistory`; not `options.isHistoryReplay`; the **confirmed** settings' normalized topN equals the intended (`"default"` or `"top-N"`); and for count topN the confirmed `topNResultValues` is non-empty. Otherwise returns a typed reason (`confirmedTopNMismatch`, `missingConfirmedTopNValues`, `historyReplay`, etc.). This is the pure extraction of `commitTopNChange`'s post-confirmation history gate — **history is only pushed for a real, confirmed, user-initiated topN change** (never on replay/restore).
- **`buildMirrorPatch(input)`** — builds the **settings patch** to mirror into the widget's persisted settings after a successful apply. For default/cleared topN: emits `topN:"default"` and **omits** `topNResultValues`/`topNExcludeItemId` (undefined). For active count topN: `topN:` the active value (`resolveActiveTopN` falls back to `"top-"+n`), plus cloned `topNResultValues` and `topNExcludeItemId` from the filter/descriptor result. Also carries `visualizationType`, `dimension`, `datasourceId`, `datasourceName`. It **does not write state** — it returns the patch for the caller to merge.

### Map to target "topN" widget type — own vs share
- **Owns (topN-specific, lives here):** the resolution **state machine** + record shape; the `parseTopNOption` contract + `top-N` normalization; the **helper-plan builders** (`buildHelperPlan`/`resolveJahrPlan`/`resolveHierarchyHelperPlan`); the **descriptor** builder; flat-data extraction; the topN history gate; the mirror patch shape; the stale guard's topN sequence preference. This is the "resolution brain".
- **Shares (cross-cutting):** `setWidgetSetting` (the `pending.*` substate + `markPending`/`clearPending` — generic per-widget state plumbing, run 1/5); the binding `seq` staleness model (`pending.binding.seq`) which `checkStaleGuard` unifies with; the helper-table **claim/cleanup + Cognos query** (run 4/7 `api/*`); the orchestrator + events (run 6a/7). A clean topN type would **own** these pure planners/descriptor/state but **delegate** the actual helper-LIST lifecycle and Cognos slot/filter writes to a shared "live/datatable helper" service.
- topN is **not its own launchpad pad** (run 6a confirmed): it's a *mode of a visualization widget*. The new `topN` type, if first-class, must still produce a chart and own a *background helper datatable* — so it inherently couples to both the `visualization` and `datatable` types.

### State & runtime touched

Mirror patch targets the widget's persisted `settings` (`topN`, `topNResultValues`, `topNExcludeItemId`, `dimension`, `visualizationType`, `datasource*`).

### Top surprises / complexity hotspots
1. **Success = delete, not a status.** The state machine has no terminal "done" — a successful `finish` calls `clearPending`. Only `pending` and `error` are ever persisted. Reading "is there a topN resolution?" means "is there a `pending` record?".
2. **Two parallel staleness mechanisms** that the guard fuses: the topN `sequenceId` (`"topN-…"`, minted here) and the generic binding `seq` (from `setWidgetSetting.nextBindingSeq`). `checkStaleGuard` prefers the topN one when the incoming id matches or is `"topN-"`-prefixed — easy to get subtly wrong.
3. **The filter is `mode:"include"` on the *exclude* item id.** The descriptor keeps the computed N members by filtering on `dimEntry.exclude.itemId` — counter-intuitive naming (exclude-id used for an include filter).
4. **Heavy hardcoded German domain specifics**: aggregation pin `AggregationstypId="Monatsdurchschnitt"`; default exclude values `["Gesamt","ALLE","^"]`; the `"jahr"` substring sniffing across `listPropObj.grid_cols`/`stackedBarPropObj.categories`; stale-label denylist `{superuser, dbversion}`; helper slot literal `"grid_cols"`.
5. **`_TM1` source-token rewriting** is pervasive and fragile — both `resolveHierarchyHelperPlan` (for the item id) and `rewriteHierarchyValues` (for each value's `.u`) re-token unique-names to `[<datasource>_TM1]`, with fuzzy `_TM1`-stripped matching to find the source key. The `#`-prefix stripping on display values is its own bespoke parser.
6. **`extractFlatData` positionally assumes `colKeys[1]` is the dimension** (value column at [0]). A single-column result silently falls back to `[0]`. No name-based lookup — purely ordinal.
7. **Stored-values fast path** (`resolveResolutionRequirement`) lets history-replay/restore skip the entire helper query — but only if both stored `topNResultValues` and `topNExcludeItemId` are present; otherwise it hard-fails rather than falling back to a live query.
8. **`buildHelperPlan`'s `cleanupPlan.releaseClaim:false`** is hardcoded — claim release is intentionally deferred to the orchestrator (`state/cancel` also refuses to release). Three separate places (`cancelTopNResolution`, `buildHelperPlan`, run-6a `cleanupWidget`) collaborate on claim lifecycle.

## RUN 7 — topN api + actions + events

Scope read in full: the 10 `…/live/topN/api/*` adapters, the 4 `…/topN/actions/*` runners, and the 5 `…/topN/events/*` modules (4 `publish*` + `subscribeTopNEvents`). Dependency peeks: `…/widgets/claimTopNHelperTable.js` (the canonical claim module all 4 claim adapters delegate to) and `…/base/events/topNEvents.js` (event-name constants). This run is the **Cognos-touching + side-effecting shell** wrapped around run 6b's pure "resolution brain" and reached through run 6a's `__topNOrchestrator`. The pure planners/descriptor/state machine were run 6b; the orchestrator entry + staleness boundary were run 6a.

### What the "helper widget" is (recap + claim reality)
The topN helper widget is **NOT a freshly-created table** — it is an **existing, already-on-canvas live LIST widget** that lives in the launchpad's `dataTables` slot and is **borrowed** for the duration of a topN computation. The visible chart can't be asked "what are your top-N members", so KDB3 finds a spare LIST table on the same tab, claims ownership, reconfigures it (datasource + slots + filters + TopBottom) to run the flat "top-N by measure" query, reads the result rows, then cleans the LIST's filters/slots back out — **but keeps the ownership claim** so the same physical table is reused for that visible widget's next topN run. The claim is **lifecycle-bound (one helper per visible widget for its whole life), not per-run** (header comment in `claimTopNHelperTable`: "helper ownership must be lifecycle-bound, not per TopN run").

### Helper-widget API — the claim→configure→render→read→cleanup/release lifecycle
The `api/*` adapters are thin, defensive wrappers. Four of them (`claim/validate/find/release`) just delegate to the canonical `claimTopNHelperTable` module; the other six do real Cognos work.

**1. Claim layer (delegating adapters → `claimTopNHelperTable.js`):**
- **`findTopNHelperCandidates(_KDB, visibleWidgetId)`** → `claimTopNHelperTable.listTopNHelperTableCandidates` (= `buildClaimCandidates`). On missing module → `{ok:false, error:"topNHelperClaimUnavailable", reason:"missingClaimModule", tableIds:[]}`.
- **`validateTopNHelperClaim(_KDB, visibleWidgetId, helperTableId)`** → `claimTopNHelperTable.validateTopNHelperClaim`. Result mirrors the claim module's validation shape.
- **`claimTopNHelperWidget(_KDB, visibleWidgetId)`** → calls `__claimTopNHelperTable__(_KDB, visibleWidgetId)` (the default export). Returns `{ok, helperTableId, reused}`.
- **`releaseTopNHelperClaim(_KDB, visibleWidgetId)`** → `claimTopNHelperTable.releaseTopNHelperTableClaim`. The file header is emphatic: **"Run cleanup is separate and must not call this adapter"** — claim release and per-run cleanup are deliberately decoupled.
- All four are pure try/catch shims that translate exceptions into typed `{ok:false, error}` failures and never throw.

**The claim model (from `claimTopNHelperTable`, dependency peek):**
- **Ownership store**: a claim is a pair of `pending.*` entries written via `setWidgetSetting.markPending` on the **helper** widget's state: `pending.topNHelperClaimedBy = <visibleWidgetId>` and `pending.topNHelperClaimedAt = Date.now()`. The visible widget back-references its helper via `canvasContext.topNHelperTableId` (`setCanvasPlacement`). So ownership is **bidirectional and serializable** (lives under `_KDB.state.widgets[*]`).
- **Reuse-first**: `__claimTopNHelperTable__` first reads the visible widget's stored `topNHelperTableId`; if that still validates (helper exists, not `removed`, `claimedBy === visibleId`) it returns `{reused:true}` without re-scanning. Only on missing/invalid claim does it scan for a new candidate.
- **Candidate scan (`buildClaimCandidates`)**: resolves the visible widget's `tabId`, finds the `dataTables` launchpad slot meta + DOM slot el, iterates `slotEl.children`. For each child it: skips self/dupes; **auto-releases orphan claims** (`cleanupOrphanClaimIfNeeded`: if the helper is claimed by a missing/`removed` widget, free it); skips helpers already claimed by *another* visible widget; requires Cognos `getType==="live"`, classifies via `classifyLiveWidgetLaunchpadPad` (must be `dataTables` or `visType==="LIST"`), and requires `getFeature("Visualization")||getFeature("DataQueryExecution")`. First surviving candidate (`tableIds[0]`) wins.
- **Race protection**: this is the **state-based claim**, distinct from run 6a's DOM `data-kdb-claimed-run` launchpad-restore attribute. Protection here = the `claimedBy` ownership check + orphan-release, not a hard lock. Two concurrent claims for *different* visible widgets won't collide (each skips the other's claimed helpers); a true simultaneous claim of the same free table is not atomically locked (last `markPending` wins), but in practice the resolution flow is awaited serially per widget.
- **Release**: `releaseTopNHelperTableClaim` clears both `pending.topNHelperClaimedBy/At` (only if owner matches or unowned) and clears the visible widget's `canvasContext.topNHelperTableId`.

**2. Context builder — `buildTopNHelperContext(_KDB, input)` (sync, pure-ish):**
The bridge from live `_KDB` snapshots into run-6b's pure planners. It resolves `parsedTopN` (`parseTopNOption` with `topNOptions` from `source` or `_KDB.dropdownOptions.hardcoded.topN`), the aggregation item id (`applyLiveWidgetLocalFilters.resolveLocalFilterItemId(_KDB, "AggregationstypId")` — fails → abort), the kennzahlen source (input → `dataConfig.kennzahlenTable` → `_KDB.state.kennzahlenSource.current`), then calls **`resolveJahrPlan`** (feeding it `properties`, page-context items via `cognosAPI.getPageContextItemsArr(true)`+`getFilterValues/getFilterItemId/getFilterItemLabel`, and `_KDB.data.tables.byName`), **`resolveHierarchyHelperPlan`** (feeding `source.hierarchySnapshot`, `dataConfig`, `properties.filterPropObj`), and **`buildHelperPlan`** (feeding all of the above + `dimensionConfig` + `aggregationItemId`). Returns `{ok, parsedTopN, kennzahlenSource, sourceKey, helperPlan, cleanupPlan, topNExcludeItemId (=helperPlan.resultExcludeItemId), jahrPlan, hierarchyPlan}`. Any sub-plan `ok===false` short-circuits to `createFailure(error)`. **This is the only place that gathers the live Cognos page-context/properties into the run-6b plan inputs.**

**3. Configure — `configureTopNHelperWidget(_KDB, input)` (async):**
Applies the deterministic plan to the claimed helper, with a **stale guard after every async boundary**. Sequence:
1. Require `helperTableId`; resolve `datasourceId` (input → `dataConfig.datasourceId` → `cognosAPI.getVizDataSourceId(visibleWidgetId)`); require it.
2. `buildTopNHelperContext` → capture `cleanupPlan`.
3. **Pre-clean** the helper (`cleanupTopNHelperWidget` with `clearAllLocalFilters:true`) — wipe any leftover state from a prior run. Then `guardCurrent`.
4. `cognosAPI.setVizDataSource(datasourceId, helperTableId)` (point the LIST at the right datasource). `=== false` → fail+cleanup. Then `guardCurrent`.
5. **Reset** (second `cleanupTopNHelperWidget`, no `clearAllLocalFilters`) — slots/filters cleared again post-datasource-swap. Then `guardCurrent`.
6. **`applyTopNHelperPlan`** (the actual slot/filter/TopBottom writes). On fail → fail+cleanup.
7. Return `{ok, helperTableId, datasourceId, helperPlan, cleanupPlan, topNExcludeItemId, jahrPlan, hierarchyPlan}`.
- `guardCurrent` wraps run-6b `checkStaleGuard` (reads `source.widgetEntry` or `_KDB.state.widgets[visibleWidgetId]`, `incomingSequenceId`, `currentSequenceId`); a non-current decision aborts with `{superseded}` and **runs `cleanupAfterFailure`** so a superseded configure doesn't leave the helper dirty. Every failure path attempts cleanup.

**4. Apply plan — `applyTopNHelperPlan(_KDB, helperTableId, helperPlan)` (sync):**
The pure-Cognos writer. Steps: `addDataItemsToSlot(helperTableId, slot.slotId, slot.itemIds)` for each `slotPlan` entry; then each `helperFilters` entry via `addOrReplaceLocalFilter(helperTableId, filter.itemId, body)` where `body` is built per-kind — `dimensionExclude` → `buildKeepexcludeConditionsFilterObj(itemId, filter)`; filters with `options` → `Object.assign({exclude: mode==="exclude", values}, options)`; else `{values}`. Then `setTopBottomOnSlot(helperId, topBottom.slotId, topBottom.n, topBottom.sortValueItemId)` (the actual "top N by measure" instruction). Finally `suppressAggregationSummary` (`setTableSummaryValue(true, id)` ‖ `setContentPropertyValue(id, "hideSummaries", true)`) so the summary row doesn't pollute the flat result. Any wrapper returning `false` → typed failure carrying `helperPlan.cleanupPlan`.

**5. Render — `renderTopNHelperWidget(_KDB, input)` (async):**
Forces the hidden helper to actually execute its query. Arms `cognosAPI.whenRenderComplete(helperTableId)` (if present), calls `cognosAPI.renderWidget(helperTableId)`, then awaits the render-complete promise via `withTimeout`. **Timeout is deliberately capped**: `Math.min(requested||15000, 2500)` — i.e. it waits **at most 2.5 s** for render-complete, because (per header) "flat-data polling remains the authoritative wait" — the real wait is `getFlatData`'s polling in `readTopNHelperResult`. A render timeout is swallowed (race resolves `null`), not treated as an error unless the promise rejects.

**6. Read — `readTopNHelperResult(_KDB, input)` (async):**
The orchestration of render+poll+extract. Requires `helperTableId`, `topNExcludeItemId`, `cognosAPI.getFlatData`, and `parsedTopN.kind==="count"` with `n>=1`. Sequence with **stale guard at each boundary**: `guardCurrent` → `renderTopNHelperWidget` → `guardCurrent` → `cognosAPI.getFlatData(helperTableId, {pick:"d", timeoutMs:15000, intervalMs:100})` (the polling fetch) → `guardCurrent` → run-6b `extractFlatData(flatData, parsedTopN)`. On success returns `{ok, applied:true, values, topNResultValues (= values copy), topNExcludeItemId, dimensionKey, colKeys, rowCount}`. Extract failures echo `colKeys`/`rowCount` for diagnostics. **This confirms run 6b's open question**: `getFlatData` with `pick:"d"` produces the `{columnDataObjArray, colKeys}` shape `extractFlatData` consumes.

**7. Cleanup — `cleanupTopNHelperWidget(_KDB, input)` (async):**
Per-run teardown that **never releases the claim** (`releasedClaim:false` always; header: "without releasing ownership"). Optionally `clearAllLocalFilters(helperTableId)`; then `Promise.all` of `removeLocalFilter(helperTableId, {itemId})` over the dedup'd `cleanupPlan.filterItemIds`; then `clearAllSlots(helperTableId)`. Each op is wrapped in `safeOp` so **one failure can't skip later cleanup** (collects `failedOps`); `ok` is true only if `failedOps` is empty. Returns `{ok, error, releasedClaim:false, clearedSlots:["grid_cols"], failedOps}`.

So the full lifecycle: **claim (reuse-or-scan) → buildContext → preClean → setVizDataSource → reset → applyPlan → render → getFlatData(poll) → extractFlatData → cleanup (filters+slots, keep claim)**, with `checkStaleGuard` between every async step, and the persistent claim released only later by the orchestrator's explicit `releaseClaim`/`cleanupWidget`.

### Action runners — the end-to-end resolution flow
- **`resolveTopNResolution(_KDB, input)` (async, top-level; called by orchestrator `requestChange`/`resolveForWidget` and the `onOptionSelected` subscription):**
  1. Require `widgetId`.
  2. `resolveResolutionRequirement` (run 6b gatekeeper) with topN/options/dimension/settings/stored-values/replay flags. `!ok` → fail.
  3. **`startTopNResolution`** (run 6b state) → mint `sequenceId`. `!ok` → return as-is.
  4. If `requirement.requiresHelperResolution !== true` → **`finishTopNNoHelperResolution`** (no helper needed).
  5. Else `await runTopNHelperResolution(...)`, then **`finishWithResult`**: `superseded` → return `{ok:false, superseded:true, cleanup*}` **without** finishing state (a newer run owns it); `!ok` → `finishTopNResolution(ok:false, error)` (writes `error` record) + `publishTopNResolutionFinished`; `ok` → `finishTopNResolution(ok:true)` (clears the pending record = success-deletes) + publish. **Header note: it returns semantic results only — applying the values to the visible widget is explicitly out of scope** (that's `configureLiveWidget`/`toHelperTableResult` in run 1/4).
- **`finishTopNNoHelperResolution(_KDB, input)` (sync):** three branches off the requirement: (a) `canUseStoredTopNValues` → **stored-values success** (echo `values`/`topNResultValues`/`topNExcludeItemId`, `applied:true`, finish ok); (b) `requiresTopNValues` (active topN but no stored values and no helper) → **`unsafeTopNNoHelperRoute` reject** (finish error) — "never returns partial success"; (c) else → **default/clear route** (`applied:false`, empty values, finish ok). All three publish `resolutionFinished`.
- **`runTopNHelperResolution(_KDB, input)` (async; the helper round-trip):**
  1. `claimTopNHelperWidget` → `helperWidgetId = claimed.helperTableId||tableId`. Missing → fail.
  2. **`isCurrent`** check (`readTopNResolution(...).isCurrent`); not current → cleanup (no helper config done yet) + `{superseded:true, error:"staleBindingSequence"}`.
  3. `updateTopNResolution` patch `{helperWidgetId}` (record the borrowed helper) → **`publishTopNResolutionRequested`** (notification: helper claimed, work starting).
  4. `configureTopNHelperWidget` → capture `cleanupPlan`. `!ok` → `finishHelperFailure` (cleanup + propagate `superseded`).
  5. `updateTopNResolution` patch `{cleanupPlan, topNExcludeItemId}` (so a later cancel/cleanup knows what to undo).
  6. `readTopNHelperResult` → then **always `resolveCleanup(..., shouldCleanup:true)`** (per-run cleanup regardless of read success). If read `!ok` → return read+cleanup; if cleanup itself failed → fail with cleanup error; else merge cleanup+read.
  7. Catch-all → cleanup + `topNHelperResolutionFailed`. **Header: it does not finish pending state and never releases the persistent claim** — finishing is `resolveTopNResolution`'s job, release is the orchestrator's.
- **`resolveTopNHelperCleanup(_KDB, input)` (async):** normalizes cleanup ownership into an observable `{cleanupResult, cleanupSummary:{performed, skipped, alreadyDoneByAdapter}}`. If the adapter already cleaned (`adapterCleanupResult` present, e.g. `configureTopNHelperWidget` cleaned on its own failure) → mark `alreadyDoneByAdapter`, don't re-clean. If `shouldCleanup !== true` or no helper id → `skipped`. Else call `cleanupTopNHelperWidget` and mark `performed`. **Purpose: prevent double-cleanup and make the runner's cleanup decisions auditable.**

### Events — 4 publishers + 1 subscriber (names from `base/events/topNEvents`)
Event-name constants: `TOP_N_OPTION_SELECTED = "topN:optionSelected"`, `TOP_N_RESOLUTION_REQUESTED = "topN:resolutionRequested"`, `TOP_N_RESOLUTION_FINISHED = "topN:resolutionFinished"`, `TOP_N_RESOLUTION_CANCELLED = "topN:resolutionCancelled"`.
- All four `publish*` modules are **structurally identical**: guard `_KDB.events.emit` exists, shallow-clone the payload (`Object.assign({}, payload)` so subscribers can't mutate caller data), `emit(eventName, payload)`, return `{ok, error, eventName}`; on missing bus or throw → typed failure. They carry **only serializable data**.
- **`publishTopNOptionSelected`** — `topN:optionSelected`. A **UI intent / flow-control trigger**: emitted (per run 6a) by the orchestrator's `publishOptionSelected`; the subscription routes it back into `resolveTopNResolution`. Payload = whatever the UI passes (widgetId, topN option, dataConfig…).
- **`publishTopNResolutionRequested`** — `topN:resolutionRequested`. A **notification**, emitted by `runTopNHelperResolution` right after claim+`updateTopNResolution`. Payload `{widgetId, helperWidgetId, sequenceId, requestedTopN: requirement.normalizedTopN}`.
- **`publishTopNResolutionFinished`** — `topN:resolutionFinished`. **Flow-control + notification**: emitted by both `resolveTopNResolution` and `finishTopNNoHelperResolution` on terminal outcome. Payload `{widgetId, sequenceId, ok, error, values, topNExcludeItemId}`. The subscription routes it to the orchestrator's `acceptResolutionFinished` (run 6a staleness gate). Header: superseded late results should **not** publish this.
- **`publishTopNResolutionCancelled`** — `topN:resolutionCancelled`. A **notification**, emitted (per run 6a) by the orchestrator's `cleanupWidget` after `cancelTopNResolution`+helper cleanup. Header: "separate from claim release."
- **`subscribeTopNEvents(_KDB, callbacks)`** — registers **idempotent** subscriptions for `onOptionSelected` (→ `optionSelected` event) and `onResolutionFinished` (→ `resolutionFinished` event). Handles stored under `_KDB.state.canvas.widgets.live.subscriptions[<key>]` (`subscribeOnce` no-ops if already subscribed). Wraps each callback in `runCallback` (catches sync throws and rejected promises → `topNSubscriptionHandlerFailed`). Returns `{ok, teardown}`; teardown `unsubscribe`s both and deletes the handles. **Note**: it only wires `optionSelected` + `resolutionFinished` — NOT `requested`/`cancelled` (those are pure notifications with no internal subscriber). And per run 6a, `subscribe()` is **never called by the production orchestrator** — the live path is the awaited `requestChange`, so these subscriptions are parallel/experimental scaffolding. This finally fills the run-6a/6b dead-scaffolding observation: the `live.subscriptions` shell ensured by `__liveOrchestrator` IS the store this subscriber writes to (so it's only "dead" because `subscribe()` is never called).

### Sequencing model: await/return vs events
- **The production path is await/return, not event-driven.** `configureLiveWidget` → orchestrator `requestChange` → `await resolveTopNResolution` → `await runTopNHelperResolution` → `await {configure, read}` and gets a structured result back. The `publish*` calls are **fire-and-forget side-channels** layered on top; the only event that has a (non-production) subscriber feeding back into logic is `optionSelected → resolveTopNResolution` and `resolutionFinished → acceptResolutionFinished`. So events here are mostly **observability/notifications**, with an unused alternative event-driven entry.
- **Staleness/supersession across the round-trip** is enforced by `sequenceId` threaded from `startTopNResolution` through *every* async hop:
  - `runTopNHelperResolution` checks `readTopNResolution(...).isCurrent` right after claim.
  - `configureTopNHelperWidget` and `readTopNHelperResult` each call `checkStaleGuard` **before and after every Cognos await** (datasource set, reset, plan apply / render, getFlatData) — a newer binding/topN sequence aborts the in-flight run with `superseded:true`, and the helper is always cleaned before returning.
  - `resolveTopNResolution.finishWithResult` refuses to finish state when `superseded` (the newer run owns the pending record), so a late result can't clobber a fresh one. State-machine `update/finish` (run 6b) independently reject non-current sequences.
  - This is a **belt-and-suspenders** model: state-level `isCurrent` (sequenceId match on the pending record) + boundary-level `checkStaleGuard` (which also fuses the generic `pending.binding.seq`).

### Map to target "topN" widget type — own vs share (consolidated, all runs)
- **MUST OWN (topN-specific):**
  - The **resolution state machine** + record (run 6b): pending/error lifecycle, success-deletes, sequenceId staleness.
  - The **helper-plan builders + descriptor + flat-data extraction + parseTopNOption** (run 6b pure brain).
  - The **helper-table claim model**: lifecycle-bound borrow of an existing `dataTables`-slot LIST, bidirectional ownership (`pending.topNHelperClaimedBy/At` ↔ `canvasContext.topNHelperTableId`), orphan-release, reuse-first.
  - The **configure→render→read→cleanup adapter sequence** with per-boundary stale guards, the **15 s flat-data poll / 2.5 s render cap**, summary suppression, and the per-run cleanup vs persistent claim-release split.
  - The **4 topN events** + the resolution action runners (the orchestration glue).
  - The **hierarchy rewrite** (`_TM1` retokenization) and **Jahr pinning** for the helper query.
- **MUST SHARE (cross-cutting infra):**
  - `setWidgetSetting` `pending.*`/`canvasContext`/`peekEntry`/`markPending`/`clearPending` — generic per-widget state plumbing.
  - The **launchpad `dataTables` slot + `findLaunchpadSlotMeta` + `classifyLiveWidgetLaunchpadPad`** — the helper IS a `datatable`-type widget parked in the launchpad; topN borrows it. → topN **structurally depends on the `datatable` type**.
  - The **Cognos wrapper facade** (`addDataItemsToSlot`, `addOrReplaceLocalFilter`, `setTopBottomOnSlot`, `setVizDataSource`, `getFlatData`, `whenRenderComplete`, `renderWidget`, `clearAllSlots`, `clearAllLocalFilters`, `removeLocalFilter`, `buildKeepexcludeConditionsFilterObj`, `getVizDataSourceId`, page-context getters) — shared with vis/datatable.
  - `applyLiveWidgetLocalFilters` (binding/slots, run 4) and the binding `seq` staleness model.
  - The **event bus** (`_KDB.events`) and the `live.subscriptions` shell.
- **topN is a *mode of a visualization widget that drives a hidden datatable*** — it is the one type that **couples both `visualization` and `datatable`**. A clean design would make topN a *capability/mixin* on the live-visualization type that delegates (a) its result rendering to the chart and (b) its compute to a shared "helper LIST query" service owned by the datatable type, keeping only the planners/state-machine/descriptor as genuinely topN-owned.

### Top surprises / complexity hotspots
1. **The helper is a borrowed existing on-canvas LIST, never created.** `buildClaimCandidates` scans the `dataTables` launchpad slot's DOM children for a spare live LIST and claims it. If the user has no spare LIST table on the tab, topN **silently can't resolve** (`topNHelperClaimUnavailable / noValidListChildInSlot`). This is a huge hidden coupling between topN and the presence of datatable widgets.
2. **Two separate cleanup-vs-release contracts, repeatedly emphasized in headers**: per-run `cleanupTopNHelperWidget` (filters/slots, `releasedClaim:false`) vs lifecycle `releaseTopNHelperClaim`. Three files explicitly warn "cleanup must not release" / "release is separate." Easy to conflate; the whole point is the helper stays claimed across runs.
3. **Render timeout capped to 2.5 s on purpose** — `renderTopNHelperWidget` looks like it waits up to 15 s but `Math.min(..., 2500)` caps it, deferring the real wait to `getFlatData`'s 15 s/100 ms poll. A reviewer would likely "fix" this as a bug.
4. **Stale guard at *every* async boundary** in configure+read, each path doing cleanup-on-supersede. Correct but verbose; supersession can abort after datasource was already swapped (cleanup restores it via slot/filter clear, but the datasource swap itself isn't reverted).
5. **`configureTopNHelperWidget` cleans the helper three+ times** (pre-clean, post-datasource reset, and on any failure). The double pre/post-datasource clean is to flush a LIST that may carry stale filters from a previous unrelated use.
6. **Two race models coexist**: run-6a's DOM `data-kdb-claimed-run` (launchpad restore) and this run's state `pending.topNHelperClaimedBy` (helper ownership). Different mechanisms, different scopes — neither is a hard lock.
7. **The event subscriber writes to the `live.subscriptions` shell that runs 6a/6b flagged as "dead scaffolding"** — it's only dead because `__topNOrchestrator.subscribe()` is never called in production. The await/return path is authoritative; the entire pub/sub layer is parallel/experimental.
8. **`resolveTopNResolution` deliberately stops at "semantic result"** — it computes values + exclude id but does NOT apply them to the visible chart. The apply lives back in `configureLiveWidget` (run 1/4), so the topN subsystem is a *pure compute service*, not a mutator of the visible widget.
9. **`finishTopNNoHelperResolution` hard-rejects the "active topN, no stored values, no helper needed" case** (`unsafeTopNNoHelperRoute`) rather than degrading — active topN must always have either a helper round-trip or valid stored values.

### Round-2 open questions
- What guarantees a spare LIST table exists in the `dataTables` slot for `buildClaimCandidates` to claim? Is there a provisioning step that ensures every tab with topN-capable charts also has a helper LIST? (If not, topN is fragile by construction.)
- `setVizDataSource` is applied to the borrowed helper but never explicitly reverted on supersede/cleanup (only slots/filters are). Does returning the helper with a changed datasource matter for the next borrower, or does the next configure's pre-clean+setVizDataSource fully reset it?
- The pub/sub layer (`subscribe`, `optionSelected`/`resolutionFinished` round-trip, `requested`/`cancelled` notifications) has no production subscriber. Is it intended for a future decoupled UI, or is it removable dead code in the redesign?
- `runTopNHelperResolution` checks `isCurrent` only once (post-claim) and relies on the adapters' internal `checkStaleGuard` thereafter; is there a window between claim and first guard where a superseding run could double-claim? (Claim reuse + serial await likely closes it, but confirm.)
- Who consumes `dimensionKey`/`colKeys`/`rowCount` returned by `readTopNHelperResult` beyond diagnostics — does `configureLiveWidget`'s `toHelperTableResult` need them, or only `topNResultValues`+`topNExcludeItemId`?
- The aggregation pin `AggregationstypId="Monatsdurchschnitt"` is resolved live via `resolveLocalFilterItemId`; what happens for datasources without that aggregation item — does buildContext abort the whole topN (it returns `createFailure(aggregationItem.error)`), and is that the desired UX?

### topN subsystem consolidated summary (runs 4 + 6a + 6b + 7)
- **Run 4 (slots/binding/live filters)** provided the shared substrate: `applyLiveWidgetLocalFilters` (the slot/filter binding primitives + `resolveLocalFilterItemId`), the local-filter descriptor application onto the *visible* widget, and the binding `seq` staleness model that topN's `checkStaleGuard` fuses with.
- **Run 6a (orchestrator entry)** is the integration seam: `__topNOrchestrator__(_KDB)` exposes `requestChange`/`resolveForWidget` (→ `resolveTopNResolution`), inline `acceptResolutionFinished` + `cleanupWidget` + `releaseClaim`, and a non-production `subscribe()`. The **only live caller is `configureLiveWidget.resolveTopNWithOrchestrator`**, which interprets `{applied, topNResultValues, topNExcludeItemId, superseded, error}` and applies values to the visible chart.
- **Run 6b (core + state)** is the pure brain: `parseTopNOption`, the helper-plan builders (`buildHelperPlan`/`resolveJahrPlan`/`resolveHierarchyHelperPlan`), `buildTopNDescriptor`, `extractFlatData`, `rewriteHierarchyValues`, the history/mirror gates, and the serializable resolution state machine (`start/update/finish/cancel/read`, success-deletes, sequenceId).
- **Run 7 (api + actions + events)** is the side-effecting shell: claim/borrow an existing `dataTables` LIST (lifecycle-bound), build live context, configure→render→read→cleanup the helper through the Cognos facade with per-boundary stale guards, and orchestrate it all via the action runners + (mostly notification-only) events.
- **End-to-end (production path)**: user/setting changes topN on a live chart → `configureLiveWidget` → `__topNOrchestrator.requestChange` → `resolveTopNResolution` (start state, check requirement) → if helper needed `runTopNHelperResolution` (claim LIST → publish requested → `configureTopNHelperWidget` → `readTopNHelperResult` (render+poll+extract) → per-run cleanup, keep claim) → finish state (success-delete or error) + publish finished → return `{topNResultValues, topNExcludeItemId, applied}` → `configureLiveWidget` writes those back as a `mode:"include"`-on-exclude-itemId local filter on the visible chart + mirrors settings. Staleness is enforced at every async hop via `sequenceId` + `checkStaleGuard`; supersession aborts and cleans without clobbering the newer run. The persistent claim survives across runs and is released only on widget cleanup/removal.
- **For the redesign**: topN should be modeled as a **capability on the live-visualization type that owns a hidden helper datatable** — owning the state machine, planners, descriptor, claim/borrow, and adapter sequence, while sharing the datatable type (for the helper), the visualization type (for the result), `setWidgetSetting`, the Cognos facade, and the binding/seq infra. The pub/sub layer is non-production and a candidate for removal or a clean replacement.
